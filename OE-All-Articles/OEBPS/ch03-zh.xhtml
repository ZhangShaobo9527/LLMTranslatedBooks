第 3 章　在缺少可观测性的情况下扩展系统带来的教训

到目前为止，我们已经定义了什么是可观测性，以及它与传统监控有何不同。我们也介绍了传统监控工具在管理现代分布式系统时的一些局限，以及可观测性如何解决这些问题。不过，从传统世界演化到现代世界，中间仍然存在一道鸿沟。如果没有可观测性就试图扩展现代系统，会发生什么？

本章通过一个真实案例，讲述团队如何一头撞上传统监控和传统架构的能力边界，并说明应用扩展时为何必须采用不同的方法。本书合著者 Charity Majors 将亲自讲述她以前在 Parse 工作期间，在缺少可观测性的情况下扩展系统所得到的教训。下面的故事以她的视角展开。

Parse 简介

亲爱的读者，你好。我是 Charity，从 17 岁起就开始值班了。当时，我在爱达荷大学安装服务器、编写 shell 脚本。我亲历了许多著名监控系统的诞生与普及，包括 Big Brother、Nagios、RRDtool、Cacti、Ganglia、Zabbix 和 Prometheus。其中大多数我都用过，虽说还没有一个不落。它们在各自所处的时代都非常有用。当我掌握了时序数据库及其界面后，所有系统问题突然都像是等待时间序列这把锤子去敲的钉子：设定阈值、监控，然后周而复始。

在我的职业生涯中，专长一直是作为第一位基础设施工程师，或者最早加入的几位之一，进入已有的软件工程团队，帮助他们把产品打磨到足以投入生产。如何才能最好地了解生产系统中正在发生什么，我已经反复做过许多次相关决策。

我在 Parse 做的正是这件事。Parse 是一个移动后端即服务（MBaaS）平台，让移动应用开发者能够把应用连接到后端云存储系统，并使用后端系统提供的 API。这个平台支持用户管理、推送通知以及社交网络服务集成等功能。2012 年我加入团队时，Parse 仍处于测试阶段。当时公司使用了一点 Amazon CloudWatch，不知怎么又同时由五套不同的系统发送告警。我把它们换成了 Icinga/Nagios 和 Ganglia，因为这些是我最熟悉的工具。

Parse 是一个很有意思的工作环境，因为它在许多方面远远走在时代前面（后来我们在 2013 年被 Facebook 收购）。早在“微服务”这个名称出现之前，更在这种架构形成浪潮之前，我们就已经采用了微服务架构。我们使用 MongoDB 作为数据存储，也几乎是与它共同成长：刚开始时使用的是 2.0 版，每个副本集只有一把锁。我们用 Ruby on Rails 开发，并且不得不给 Rails 打猴子补丁，才能支持多个数据库分片。

我们的多租户架构很复杂，并使用共享的租户资源池。早期阶段，我们的优化目标只有一个：开发速度。

这里我要停下来强调，为开发速度而优化是正确的选择。这个决定使我们早期做出的许多选择后来不得不推倒重来。但大多数初创公司并不是因为工具选错了才失败。说得直白一些：大多数初创公司都会失败。失败的原因可能是产品没有需求、找不到产品与市场的契合点、客户不喜欢做出来的东西，或者其他无数种必须争分夺秒解决的问题。选择 MongoDB 和 Ruby on Rails 组成的技术栈，让我们得以及时把产品推向市场、赢得客户喜爱，而客户也希望得到更多我们所提供的服务。

Facebook 收购 Parse 时，我们托管了 6 万多个移动应用。两年半后，我离开 Facebook 时，这个数字已经超过 100 万。但其实早在 2012 年我刚加入时，裂痕就已开始显现。

我加入几个月后，Parse 正式发布。流量先翻一倍，再翻一倍，随后又翻了一倍。我们是 Hacker News 的宠儿，每次那里出现介绍 Parse 的帖子，都会带来一波注册高峰。

2012 年 8 月，我们托管的一个应用首次进入 iTunes Store 前十名。这个应用用于推广一支来自挪威的死亡金属乐队，乐队通过它进行直播。乐队开播时是当地傍晚，对 Parse 而言却是黎明。每次直播一开始，Parse 都会在几秒钟内彻底宕机。我们的扩展能力出了问题。

Parse 的扩展过程

起初，要弄清我们的服务究竟发生了什么非常困难。由于采用了租户共享模型，只要有任何一处变慢，所有地方都会一起变慢，即使它们与真正的问题原因毫无关系，因而诊断尤其棘手。

要解决这一整组问题，我们只能不断试错和调整。我们必须提升 MongoDB 数据库管理能力。经过大量工作后，终于查明了问题来源。为了减轻同类问题日后再次出现时的影响，我们编写了工具，可以有选择地限制特定应用的流量，或者即时改写、限制结构不佳的查询。我们还专门为那支挪威死亡金属乐队的用户 ID 制作了 Ganglia 仪表板，以便今后迅速判断事故是不是它造成的。

这个过程十分艰难，但我们最终控制住了局面。所有人都松了一口气，然而这仅仅是开始。

Parse 让移动应用开发者可以轻松创建新应用，并迅速发布到应用商店。我们的平台大获成功，开发者非常喜欢这种体验。于是日复一日，他们不断这样发布应用。很快，每周都会有好几个由 Parse 托管的新应用迅速冲上 iTunes Store 或 Android Market 榜首。这些应用会借助我们发送推送通知、保存游戏状态、执行复杂的地理位置查询，工作负载完全无法预测。无论白天还是深夜，随时都可能有数百万条设备通知在毫无预警的情况下涌入 Parse 平台。

就在这时，我们开始遭遇当初所选架构、所用语言，以及用来理解这些选择的工具中存在的许多根本缺陷。我要再次强调：每一个选择在当时都是正确的。我们迅速进入市场，找到了自己的定位，也成功交付了产品。现在的问题是，如何成长到下一个阶段。

这里先暂停一下，介绍我们做过的一些决策，以及规模扩大后它们造成的影响。API 请求进入系统后，先经过负载均衡，再交给一组称为 Unicorn 的 Ruby on Rails HTTP 工作进程。我们的基础设施运行在 Amazon Web Services（AWS）上。每个 Amazon Elastic Compute Cloud（EC2）实例都托管一个 Unicorn 主进程，由它派生出二十多个 Unicorn 子进程，实际处理 API 请求。Unicorn 会与多个后端保持套接字连接：MySQL 存放内部用户数据，Redis 处理推送通知，MongoDB 存放用户定义的应用数据，Cloud Code 在服务端容器中执行用户提供的代码，Apache Cassandra 用于 Parse 分析，等等。

这里必须注意，Ruby 不是采用原生线程模型的语言，因此 API 工作进程池的容量是固定的。只要某个后端处理请求的速度稍有下降，进程池很快就会被等待该后端响应的请求占满。后端一旦变得非常缓慢，甚至完全没有响应，进程池会在几秒钟内耗尽，整个 Parse 随即宕机。

起初，我们通过超额配置实例来应对这个问题：在正常稳定状态下，Unicorn 的利用率只有 20%。这种方法让我们能够挺过一些程度较轻的降速。但与此同时，我们也作出了一个痛苦的决定：把系统从 Ruby on Rails 完整改写为 Go。我们意识到，要摆脱这个困境，唯一的出路是采用原生支持线程的语言。最初用一年写成的代码，改写却花了两年多。在这段时间里，我们站在最前沿，亲身经历了传统运维方法与现代架构问题从根本上不相容的种种表现。

对整个 Parse 而言，这是一段格外残酷的时期。我们的运维工程团队经验丰富，也在做所有公认“正确”的事情。然而我们逐渐发现，那些源自传统方法、人人熟知的最佳实践，根本不足以应对现代分布式微服务时代的问题。

在 Parse，我们全面采用基础设施即代码。我们拥有一套复杂的 Nagios 检查、PagerDuty 告警和 Ganglia 指标系统，还有数以万计的 Ganglia 图表和指标。但这些工具辜负了我们，因为只有当我们事先知道问题会是什么、合理阈值是多少、应该去哪里查看时，它们才有价值。

例如，只有当我们知道该精心编排哪些仪表板，能够预先猜到诊断问题需要哪些自定义指标时，时序数据库图表才有价值。只有当我们大致知道要寻找什么，记得提前记录正确的信息，并且知道该用什么正则表达式搜索时，日志工具才有价值。只有当问题恰好表现为应用性能管理（APM）工具所关注的十大异常查询、异常用户或异常端点之一时，这些工具才非常有用。

然而，我们面对的是一大批这些方案根本无力解决的问题。遇到以下情况时，上一代工具已经力不从心：

  • 每隔一天，就会有一位全新的用户迅速冲进某个移动应用商店的前十名。

  • 网站宕机的原因，并不是任何一份前十名榜单上那些用户产生的负载。

  • 慢查询列表中的内容全都只是问题的症状，而非原因。例如，大量极小的写操作共同把锁资源推到极限，导致读取查询变慢；但单独来看，每次写操作几乎都会立即返回。

  • 我们需要看清这样一种情况：网站总体可靠性虽然达到 99.9%，但剩余的 0.1% 并没有均匀分布到所有用户身上。这 0.1% 实际上意味着某一个分片完全不可用，而恰巧那一个分片存放了某家以老鼠为吉祥物、价值数十亿美元的著名娱乐公司的全部数据。

  • 每天都可能冒出一个新的机器人账号，执行某些操作，把 MySQL 主库的锁占用率推到极限。

这类问题与上一代问题有着本质区别，而那些工具正是为上一代问题构建的。它们服务于一个一切皆可预测的世界。当时，生产软件系统只有“一个应用”和“一个数据库”：应用的全部功能与复杂性集中在一个地方。但如今，扩展意味着把单体应用拆成许多服务，供众多不同租户使用；也意味着把单一数据库拆成种类繁多的存储系统。

包括 Parse 在内的许多公司，其商业模式都把产品变成了平台。我们邀请用户在托管服务上运行他们愿意运行的任何代码，也邀请他们对托管数据库执行任何想执行的查询。就这样，为了争夺市场收入，我们原本对系统拥有的控制力突然烟消云散。

在服务即平台的时代，客户喜爱我们赋予他们的强大能力。这股动力彻底改变了软件行业。而对于负责运行平台底层系统的人来说，这意味着系统不仅在运维和管理上变得极其困难，甚至是成倍地困难，就连理解系统也同样如此。

我们是如何走到这一步的？行业又是在何时仿佛一夜之间发生了变化？下面看看一系列细小的迭代，如何最终汇成这场翻天覆地的转变。

向现代系统演化

最初，在互联网繁荣期的早些年，系统只有“一个应用”和“一个数据库”。它们很容易理解：要么正常，要么宕机；要么慢，要么不慢。我们只需监控它们是否存活，以及响应速度是否处于可接受阈值内。

这项工作并非总是轻而易举，但从运维角度看十分直接。有很长一段时间，我们甚至围绕一种架构简洁性的典范来构建系统。当时最流行的架构模式是 LAMP 技术栈，即 Linux、Apache、MySQL，以及 PHP 或 Python。你大概已经听过下面这句话，但我现在还是有义务再说一次：如果 LAMP 技术栈或同类方案能够解决你的问题，那你很可能就应该使用它。

设计服务架构的第一条原则是不要增加不必要的复杂性。你应该仔细识别真正需要解决的问题，并且只解决这些问题。认真考虑哪些选择需要留有余地，然后保留这些余地。因此，大多数时候都应该选择乏味的技术。不要把乏味误解成糟糕。所谓乏味，只是指它的边界情况和故障场景已经被许多人充分理解。

然而，面对当今用户的需求，越来越多的人发现，许多必须解决的问题已经无法依靠朴实却强大的 LAMP 技术栈处理。原因可能多种多样：你也许需要更高的可靠性，而 LAMP 无法提供所需的韧性保证；也许数据量太大，或者数据过于复杂，LAMP 难以妥善处理。通常，我们是为了规模、可靠性或速度而触及这种简单架构模型的边界；正是这些需求促使我们对技术栈进行分片、分区或复制。

管理代码的方式也很重要。在规模更大或更加复杂的环境中，单体代码仓库会产生组织压力，进而推动技术变化。拆分代码库可以划分出更清晰的责任范围，使组织行动得比所有人共同维护“那一个庞大应用”时更加迅速、更加自主。

这些需求以及更多其他因素，共同推动了现代系统架构发生清晰而显著的转变。在技术层面，这些变化主要产生了以下影响：

  • 一切都从单个整体拆分为多个部分。

  • 数据存储需要多样化，从一个数据库变为多种存储系统。

  • 从单体应用迁移到大量规模较小的微服务。

  • 基础设施从“大型主机”转向容器、函数、无服务器架构以及其他短暂存在且可弹性伸缩的资源，类型变得更加多样。

这些技术变化也在人和组织层面引发了强烈的连锁反应：我们的系统是社会技术系统。这些转变在社会层面引入的复杂性及其反馈循环，又进一步推动了系统本身以及我们理解系统的方式发生变化。

想想 LAMP 技术栈最流行的年代，人们通常会把哪些社会特征与当时的计算环境联系起来。运维团队与开发团队之间隔着一道高高的组织壁垒，代码偶尔才会被扔过这堵墙。运维团队出了名地抗拒对生产系统作出变更，因为部署变更会产生不可预测的行为，而且往往可能造成宕机。因此，他们禁止开发者直接接触生产环境，谨慎守护系统的正常运行时间。在这种“玻璃城堡”式的方法中，冻结部署是维持生产服务稳定的常用手段。

在 LAMP 技术栈时代，这种保护生产环境的方法也不完全错误。当时，生产系统中的许多混乱确实是由引入不良代码造成的。部署新代码后，结果基本是非黑即白：网站要么正常，要么宕机（如果运气不佳，偶尔还会出现第三种状态：莫名其妙地变慢）。

当年几乎没有如今司空见惯的架构机制，能够控制不良代码带来的副作用，也不存在服务的优雅降级。如果开发者在一个看似无关紧要的小组件中引入缺陷，例如导出功能，那么每次有人使用它时，整个系统都可能崩溃。没有任何机制能暂时禁用这些后来证明并不次要的子组件，也无法只修复损坏的子系统，而让服务其他部分继续不受影响地运行。有些团队会尝试给单体应用加入这种细粒度控制，但这条路危险重重、困难重重，以至于大多数团队甚至不会尝试。

无论如何，许多单体系统仍在不断膨胀。随着越来越多的人试图在同一片代码路径上协作，锁竞争、成本上限和动态资源需求等问题逐渐成为无法逾越的障碍。从一个整体转向多个部分的巨变，对这些团队来说已不可避免。单体应用迅速被拆解成分布式系统，并随之产生了二阶影响：

  • 服务可用性不再只是正常或宕机两种简单状态，而要用复杂的可用性判断方法表示各种局部故障或降级状态。

  • 相对简单的生产代码部署方案转向渐进式交付。

  • 过去部署后代码路径立即改变、功能立即上线；后来则转向晋级式方案，借助功能标志把代码部署与功能发布解耦。

  • 过去生产环境只运行应用的一个当前版本；后来通常会有多个版本同时在生产环境中接受验证。

  • 过去由公司内部运维团队管理基础设施；后来许多关键基础设施组件由其他公司的其他团队运行，并被抽象到 API 背后，作为开发者的你甚至可能根本无法接触它们。

  • 过去的监控系统很适合针对已经遇到的已知故障发出告警并排查问题；进入分布式世界后，它们却严重力不从心，因为从未出现、甚至可能永远不会再次出现的未知故障，已经成为新的常见问题。

说明

渐进式交付一词由 RedMonk 联合创始人 James Governor 提出，指一组围绕受控、局部地向生产环境部署代码或变更的技能与技术，例如金丝雀发布、功能标志、蓝绿部署和滚动部署。

管理 LAMP 技术栈等单体系统所需的工具和技术，用于运行现代系统时完全无效。应用通过一次“大爆炸式”发布整体部署的系统，与微服务的管理方式截然不同。使用微服务时，应用往往分部分逐步推出；而且由于功能标志可以在无须部署的情况下启用或禁用代码路径，部署代码也不一定等于发布功能。

同样，在分布式世界中，预发布系统已经不如过去有用，也不如过去可靠。即使在单体架构时代，要在预发布环境中复刻生产环境也一直很困难；如今进入分布式世界，这实际上已经不可能做到。这意味着在预发布环境中调试和检查不再有效，我们不得不转向直接在生产环境中完成这些工作的模式。

向现代实践演化

系统的技术层面与社会层面彼此关联。既然面对的是社会技术系统，那么推动技术转向不同的性能模型时，也必须改变决定团队如何工作的模型。

而且这些转变紧密交织，根本无法在它们之间画出清晰边界。上一节描述的许多技术变化，都迫使团队重新组织并改变实践方式，才能提供相应支持。

不过，有一个方面的社会行为变化格外清晰。向现代分布式系统演化还会带来三阶影响，改变工程师必须与生产环境建立的关系：

  • 不能再把所有服务用户的体验概括成完全相同。在新模型中，不同用户的请求可能沿不同路径通过系统，使用不同组件，得到的体验也可能差异巨大。

  • 如果监控告警专门寻找生产环境中超过已知阈值的系统边界状况，就会产生大量误报、漏报和毫无意义的噪声。告警模式已经转变：只关注直接影响用户体验的症状，从而减少触发的告警数量。

  • 调试器无法再附加到某个特定运行时。如今，要完成服务请求必须跨越网络、经过多个运行时，而且单个请求往往要这样往返多次。

  • 需要人工修复并能写进运行手册的已知重复故障，已经不再是常态。服务故障已经转向另一种模式：已知的重复故障可以自动恢复；无法自动恢复并因此触发告警的故障，很可能意味着响应告警的工程师将面对一个全新问题。

这些三阶信号表明，关注重点正在发生巨大的引力转移：预生产的重要性下降，深入了解生产环境的重要性上升。过去那种在代码进入生产环境之前竭力加固代码、确保安全的做法，开始被认为限制重重，而且有些徒劳。测试驱动开发以及在预发布环境中运行测试仍然有用，但永远无法复刻代码在生产环境中会被如何疯狂且不可预测地使用。

作为开发者，我们能够投入工作的精力总量是固定的。传统方法的局限在于，它首先把注意力集中在预生产加固上；如果最后还能剩下一点零碎精力，才会分给生产系统。如果我们希望在生产环境中构建可靠服务，就必须把这个优先顺序颠倒过来。

在现代系统中，我们必须首先把大部分工程精力和工具投入生产系统，余下的精力再用于预发布和其他预生产系统。预发布系统确实有价值，但它只能居于次要位置。

预发布系统不是生产系统，永远无法复刻生产环境中正在发生的事情。预生产系统如同无菌实验室，绝不可能模拟付费用户在现实世界中检验代码时的真实条件。然而，许多团队仍然把生产环境视为一座玻璃城堡。

工程团队必须重新确定生产环境的价值优先级，并相应改变实践方式。如果不把生产系统转为首要关注点，团队就只能继续使用低劣的工具、有限的可见性和可观测性，在生产系统上辛苦劳作。他们仍会把生产环境视为脆弱禁地，不敢轻易涉足；只要看到一丝潜在问题，就会本能而熟练地回滚部署。之所以如此，是因为他们没有足够的控制能力，无法针对自己已经透彻理解的问题进行小幅修改、调整设置、让服务温和降级或渐进式部署变更。

技术向现代系统演化，也会带来社会层面的演化，工程团队因而必须改变与生产环境的关系。不改变这种关系的团队，将更强烈地承受由此带来的痛苦。在现代系统中，生产环境越早不再被当作玻璃城堡，负责这些系统的团队就能越早改善工作生活，使用系统的客户也能越早获得更好的体验。

Parse 的实践转变

为了迅速扩展 Parse，我们不得不以相当痛苦的方式完成这些转变。但它们并没有在一夜之间发生。传统实践是我们唯一熟悉的方法。就我个人而言，我只是在沿用过去多次管理其他公司生产系统时走过的那条公认路径。

每当出现新问题，例如那支挪威死亡金属乐队造成的故障，我都会一头扎进去进行大量调查，直到找到问题来源。团队会开展事故复盘、剖析问题，编写运行手册告诉未来的自己如何处理，再精心制作一两块自定义仪表板，确保下次问题出现时立刻显现。随后，我们就继续前进，认为这个问题已经解决。

这种模式很适合单体系统，因为其中真正的新问题十分罕见。Parse 最早期使用它也很有效。但对于现代系统，真正的新问题很可能占遇到的绝大多数，这种模式就完全无效。当我们每天开始遭受大量类别各异的问题轰炸时，这套方法有多徒劳已经不容否认。在这种环境下，我们用于事故复盘、创建运行手册和精心制作自定义仪表板的全部时间，几乎都被浪费了，因为同样的问题再也不会出现。

传统方法的现实是，其中有太多环节都在靠猜。在其他系统中，我非常擅长猜测哪里可能出了问题，几乎毫不费力。我与自己的系统在直觉上高度合拍，只需扫一眼一组复杂的仪表板，就能自信地告诉团队：“问题在 Redis。”即使屏幕上根本没有显示 Redis，我也能这样判断。我为这种技术直觉感到骄傲。这很有趣，让我觉得自己像个英雄。

我要特别强调软件行业中这种英雄文化。对于采用 LAMP 技术栈式运维的单体系统，走投无路时最后求助的调试者，通常是在团队时间最久、从零开始构建系统的那个人。资历最深的工程师是最终升级求助的对象。他们受过最多挫折，脑中积累的事故目录也最庞大，最后总是由他们从天而降、挽救局面。

结果是，这些英雄永远无法真正休假。我还记得自己在夏威夷度蜜月时，凌晨 3 点收到告警，因为 MongoDB 不知怎么拖垮了 Parse API 服务。我的老板，也就是 CTO，万分抱歉。但网站确实宕机了，而且已经停了一个多小时，没有人查得出原因，所以他们只能呼叫我。没错，我抱怨了；但在内心深处，那种感觉其实很好。我被需要，不可或缺。

如果你曾值班管理生产系统，可能会认出这种模式。英雄文化非常糟糕：对公司没有好处，对英雄本人也没有好处，因为它会造成严重的职业倦怠；对于后来加入的每一位工程师，它更令人沮丧，因为他们会觉得除非资深工程师离开，否则自己永远没有机会成为“最优秀”的调试者。这种模式完全没有必要，而最重要的是，它无法扩展。

为了应对 Parse 的扩展难题，我们必须把使用旧方法处理新问题时白白浪费的宝贵时间重新投入其他地方。当时我们拥有的许多工具，以及软件行业至今仍然依赖的许多工具，都是为模式匹配而设计的。更确切地说，它们帮助专家级资深工程师把过去遇到的问题，与同一主题下出现的新变体进行模式匹配。我从未质疑过这一点，因为那已经是当时最好的技术和流程。

Facebook 在 2013 年收购 Parse 后，我接触到了 Scuba，这是 Facebook 用于大多数实时分析的数据管理系统。这个快速、可扩展的分布式内存数据库每秒可以摄取数百万行事件数据。它把实时数据完全保存在内存中，处理查询时再跨数百台服务器进行聚合。最初的使用体验并不好。我觉得 Scuba 的用户体验丑陋得咄咄逼人，甚至带有敌意。但有一件事它做得极其出色，也永久改变了我排查系统问题的方法：它让我能够以近乎实时的速度，沿基数无限高的维度任意切分和细查数据。

我们开始把一部分应用遥测数据集发送到 Scuba，并尝试它的分析能力。查明新问题来源所需的时间骤然缩短。过去采用传统的模式匹配方法时，我们可能要花几天，甚至也许永远无法弄清发生了什么。现在，借助能沿任意高基数维度随意切分和细查数据的实时分析，这段时间缩短到几分钟，甚至几秒钟。

调查新问题时，我们可以从症状出发，沿着“面包屑线索”一路走向答案，无论线索通向哪里，也无论此前是否遇到过同类问题。我们无须先熟悉问题才能解决它。现在，我们拥有了一套可分析、可重复的方法：提出一个问题、取得答案，再根据答案提出下一个问题，直到找到根源。排查生产问题意味着从数据出发，坚持不懈地、一步接一步地沿有条理的路径前进，直到得出解决方案。

这种新能力彻底改变了我们的实践，而且再也没有回头。过去，我们依赖的是个别工程师头脑中封闭保存的系统内幕和事故目录，其他队友无法接触；现在，我们拥有了所有人都能在共享工具中看到和使用的数据与方法。对团队而言，这意味着我们可以沿着彼此的脚步前进、回溯彼此走过的路径，并理解其他人的思考过程。这项能力使我们摆脱了依赖模式匹配型工具的陷阱。

使用指标和传统监控工具时，我们很容易看到性能尖峰，或者注意到问题可能正在发生。但这些工具不能让我们任意切分和细查数据、逐层深入技术栈以找出问题来源，也无法揭示那些除此之外根本无从发现的错误相关性。调查一个新问题之前，它们还要求我们预先猜测哪些数据可能有价值，仿佛问题尚未出现时，我们就知道届时需要提出哪些问题。日志工具也是如此：必须记得提前记录所有可能有用的信息，而且调查需要时还得确切知道该搜索什么。使用 APM 工具时，我们可以快速看到工具厂商预测最值得了解的问题；但当新问题成为常态时，这种能力几乎帮不上忙。

完成这次范式转变后，最优秀的调试者不再是在团队待得最久的人，而是最好奇、最坚持不懈，并且最熟练掌握新分析工具的人。这样一来，每个人都能平等地接触系统，以及工程师群体共享的智慧。

把每个问题都当成新问题，我们就能在生产环境出现异常时查明真正发生了什么，而不是简单地把它与过去最相似的问题进行模式匹配。由此，我们可以有效排查那些采用传统方法时最难处理的系统。

现在，我们可以快速而有效地诊断以下问题：

  • 微服务，以及跨越多个运行时的请求。

  • 异构存储系统，而且无须精通其中每一种系统。

  • 多租户，以及同时运行服务端代码与查询的环境；我们可以轻松下钻到单个用户的体验，确切了解正在发生什么。

即使对于少数仍然采用乏味技术、所有潜在问题都已被充分理解的单体系统，我们也得到了一些收益。我们未必发现了什么新东西，但因此能够更加迅速、更有信心地发布软件。

在 Parse，真正让我们的处理方法能够随规模扩展的，是学会如何与一个可观测的系统打交道。我们以恰当的抽象层次收集应用遥测数据，围绕用户体验进行聚合，并且能够实时分析，从而获得了近乎神奇的洞察力。一旦能够提出任何问题、追踪任意步骤序列，并且只通过观察应用的输出就理解任何系统内部状态，传统工具的局限也就被消除了。拥有可观测性以后，我们终于能够让自己的实践走向现代化。

结语

这段发生在我供职 Parse 期间的经历，说明了组织为何以及如何从传统工具和监控方法，转向利用现代分布式系统和可观测性来扩展自身实践。2015 年，我离开 Facebook；不久以后，Facebook 宣布即将关闭 Parse 托管服务。此后，随着软件行业转而采用类似技术，我和团队在管理现代分布式系统时遇到的许多问题只变得更加普遍。

Liz、George 和我认为，正是这种转变解释了为什么可观测性会引起如此高涨的热情并日益普及。扩展现代系统时出现了许多常见问题，而可观测性正是解决这些问题的方案。后续章节将探讨可观测性的众多层面、影响和收益。
