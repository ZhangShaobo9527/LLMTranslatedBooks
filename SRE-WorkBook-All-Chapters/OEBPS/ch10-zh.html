第 10 章　事后复盘文化：从失败中学习

作者：Daniel Rogers、Murali Suriar、Sue Lueder、
Pranjal Deo 和 Divya Sudhakar，
Gary O’Connor 和 Dave Rensin 参与撰写

我们的经验表明，真正的无责事后复盘文化能够造就更可靠的系统。因此，我们认为，这项实践对于建立并维持一个成功的 SRE 组织至关重要。

在组织中引入事后复盘，既是文化变革，也是技术变革。这样的转变看似艰巨。本章最重要的信息是：这种改变完全可以实现，不必把它视为无法逾越的挑战。不要在事件结束后只是期待系统最终自行解决问题。可以先引入最基本的事后复盘流程，再不断反思和调整，使之最适合自己的组织；和许多事情一样，这里没有放之四海而皆准的方案。

如果事后复盘写得好、后续行动得到落实，并且成果得到广泛分享，它就能成为推动组织积极变革、避免故障重演的有力工具。为说明优秀事后复盘的写作原则，本章以 Google 的一次真实故障为案例。我们先用一份写得较差的复盘说明不良做法为何会损害健康的复盘文化，再将其与事件后的真实复盘对照，提炼高质量复盘的原则与最佳实践。

本章后半部分将分享我们在建立激励机制、培育稳健复盘文化方面的经验，并说明如何识别和纠正这种文化开始失效的早期迹象。

最后，我们提供一些工具和模板，帮助你从零开始建立事后复盘文化。

有关无责事后复盘理念的全面讨论，请参阅第 15 章，见我们的第一本书《Site Reliability Engineering》。

案例研究

本案例始于一次例行机架退役，却导致用户所感受到的服务延迟上升。维护自动化中的一个缺陷，加上速率限制不足，使数千台承载生产流量的服务器同时下线。

Google 的大多数服务器位于自有数据中心，但我们也在主机托管设施（colo）中部署代理／缓存服务器机架。包含这些代理服务器的 colo 机架称为卫星节点。卫星节点需要定期维护和升级，因此任何时刻都有一些卫星机架正在安装或退役。在 Google，这些维护流程大多已经自动化。

退役流程会通过一种称为 diskerase 的机制覆写机架内所有磁盘的全部内容。机器一旦被送入 diskerase，原先存储的数据便无法恢复。典型的机架退役步骤如下：

# Get all active machines in "satellite"
machines = GetMachines(satellite)

# Send all candidate machines matching "filter" to decom
SendToDecom(candidates=GetAllSatelliteMachines(),
            filter=machines)

案例中的卫星机架已被标记为退役。退役流程的 diskerase 步骤成功完成，但负责其余机器退役工作的自动化流程失败了。为调试该故障，我们重新执行了退役流程。第二次执行过程如下：

# Get all active machines in "satellite"
machines = GetMachines(satellite)

# "machines" is an empty list, because the decom flow has already run.
# API bug: an empty list is treated as "no filter", rather than "act on no
# machines"

# Send all candidate machines matching "filter" to decom
SendToDecom(candidates=GetAllSatelliteMachines(),
            filter=machines)

# Send all machines in "candidates" to diskerase.

几分钟内，全球所有卫星节点机器的磁盘都被擦除。这些机器随即失效，无法再接受用户连接，后续连接因此被直接路由到数据中心。结果是用户延迟略有上升。得益于良好的容量规划，在受影响的 colo 机架重新安装机器所需的两天里，只有极少数用户注意到问题。事件发生后，我们用了数周审计自动化流程并增加更多合理性检查，使退役工作流具备幂等性。

这次故障三年后，我们又遇到了一起类似事件：一些卫星节点被排空流量，导致用户延迟上升。原始事后复盘中行动项的落实，显著缩小了第二次事件的影响范围，并减缓了其发展速度。

假设由你负责为这个案例撰写事后复盘。你希望了解哪些信息？又会提出哪些行动，以防止这类故障再次发生？

先来看一份写得不太好的事件事后复盘。

术语表

为什么这份事后复盘很糟糕？

这份“糟糕的”事后复盘包含了许多我们努力避免的常见问题。以下各节说明如何改进。

缺少上下文

这份示例复盘一开始就引入了 Google 流量服务领域（如“卫星节点”）和机器管理自动化底层（如“diskerase”）的专用术语。若复盘需要补充背景，应使用“背景”和／或“术语表”部分，也可以在其中链接更长的文档。本例中，这两部分都是空白的。

撰写事后复盘时，如果没有为内容提供恰当的上下文，文档就可能被误解，甚至被忽略。务必记住，读者并不只限于直接参与事件的团队。

省略关键细节

多个部分只有概要，却缺少重要细节。例如：

问题摘要

对于影响多项服务的故障，应提供数字，以一致的方式呈现影响。示例中唯一的数值数据只有问题持续时间，信息不足以估算故障规模或影响。即使没有确切数据，有依据的估算也胜过完全没有数据。毕竟，如果不知道如何衡量，就无法判断问题是否真的已经解决。

根因和触发因素

确定根因和触发因素，是撰写事后复盘最重要的目的之一。示例虽然用一个短段落描述了根因和触发因素，却没有深入探究问题的底层细节。

恢复工作

事后复盘是留给读者的事件记录。好的复盘会让读者了解发生了什么、问题如何得到缓解，以及用户受到怎样的影响。这些问题的答案通常位于“恢复工作”部分，而本例中的该部分却是空白的。

如果一次故障值得开展事后复盘，就也应投入时间，准确记录必要的细节。读者应当获得故障的完整图景，更重要的是，能从中学到新知识。

行动项缺少关键要素

示例中的“行动项”部分缺少防止事件重演所需的可执行计划的核心要素。例如：

  • 这些行动项大多只是缓解措施。为尽量降低故障重演的概率，还应加入一些预防性行动项和修复措施。唯一一项所谓的“预防”措施，是让“人更不容易犯错”。一般而言，改变人的行为不如改变自动化系统和流程可靠。（正如 Dan Milstein 曾打趣道：“规划未来时，就假定那时的我们和今天一样愚蠢。”）

  • 所有行动项都标成了相同优先级，无法判断应先处理哪一项。

  • 列表前两项使用了“改进”“做得更好”之类含糊措辞。这些词语意义不明确，解释空间很大；措辞不清会使成功标准难以理解和衡量。

  • 只有一项行动项关联了跟踪缺陷。没有正式跟踪流程时，事后复盘中的行动项往往会被遗忘，进而导致故障再次发生。

说明

Google 负责全天候运维的副总裁 Ben Treynor Sloss 曾说：“对用户而言，没有后续行动的事后复盘，和根本没有复盘没有区别。因此，凡是影响用户的故障，其事后复盘都必须至少关联一个 P[01] 缺陷。例外情况由我亲自审核，而例外极少。”

适得其反的指责

任何事后复盘都有可能滑向指责式叙事。来看几个例子：

做得不好的方面

复盘把故障归咎于整个团队，同时还特别点名了两名成员（maxone@ 和 logantwo@）。

行动项

列表最后一项把矛头指向 sydneythree@，指责其屈从于压力并错误处理跨站点交接。

根因和触发因素

dylanfour@ 被认定为该故障的唯一责任人。

在事后复盘中点名个人看似合理，实际却会让团队成员因害怕公开受辱而趋于规避风险，甚至可能促使他们隐瞒理解事件、防止重演所必需的关键事实。

情绪化语言

事后复盘是一份事实性记录，不应包含个人评判和主观措辞。它应兼顾多方视角，并尊重他人。示例复盘中有多处不当表述：

根因和触发因素

画蛇添足的措辞（如“疏忽无知”）

做得不好的方面

情绪化措辞（如“这太荒谬了”）

侥幸之处

难以置信式的感叹（如“真不敢相信我们竟挺过了这次事故！！！”）

情绪化语言和戏剧化的事件描述会分散读者对关键信息的注意力，并削弱心理安全感。应改用可验证的数据来说明陈述的严重程度。

责任归属不清

明确正式负责人会形成问责，进而推动行动。示例复盘中有多处责任归属不清：

  • 该复盘列出了四名负责人。理想情况下，应指定一名单一联系人，对复盘本身、后续跟进和最终完成负责。

  • “行动项”部分的条目很少指定负责人，甚至完全没有。没有明确负责人的行动项更难得到落实。

最好有一个负责人和多个合作者。

受众有限

示例复盘只在团队成员之间共享。默认情况下，公司所有人都应能访问该文档。我们建议主动尽可能广泛地分享复盘，甚至可以与客户分享。复盘的价值与其带来的学习成正比：能从既往事件中学习的人越多，事件重演的可能性就越低。经过深思熟虑且坦诚的复盘，也是修复受损信任的重要工具。

随着经验积累、团队更加从容，复盘的“受众”很可能还会扩展到非人类系统。成熟的复盘文化通常会加入机器可读的标签和其他元数据，以支持下游分析。

发布延迟

示例复盘在事件发生四个月后才发布。在这期间，若事件再次发生（现实中确实发生了），团队成员很可能已经忘记本可由及时复盘记录下来的关键细节。

根因与触发因素

手动重新执行 a12bcd34 卫星节点的退役工作流，触发了流量管理服务器中一个长期存在的输入验证缺陷。该缺陷移除了退役操作中的机器范围约束，导致所有卫星节点机器都被送去退役。

随后，数据中心自动化系统执行退役工作流；在操作被制止前，大多数卫星节点机器的硬盘已经被擦除。

流量管理服务器提供 ReleaseSatelliteMachines RPC。该处理程序通过三次 MDB API 调用发起卫星节点退役：

  • 查找与边缘节点关联的机架名称（例如 a12bcd34 → <机架名称>）。

  • 查找与该机架关联的机器名称（<机架> → <机器 1>、<机器 2>，依此类推）。

  • 将这些机器重新分配给 diskerase，从而间接触发退役工作流。

由于 MDB API 的一种已知行为，再加上缺少安全检查，该流程并不幂等。如果某个卫星节点此前已成功进入退役流程，上述第 2 步就会返回空列表；第 3 步则会把空列表解释为“不对机器主机名施加任何约束”。

这种危险行为存在已久，却被调用不安全操作的工作流掩盖了：调用该 RPC 的工作流步骤被标记为“仅运行一次”，即 RPC 一旦成功，工作流引擎便不会再次执行它。

然而，“仅运行一次”的语义不跨工作流实例生效。集群启用团队为 a12bcd34 手动启动另一个工作流实例时，便触发了 admin_server 缺陷。

经验教训

做得好的方面

  • 撤空边缘节点。核心集群中的 GFE 和生产骨干网都明确按可承接这类流量进行容量规划（对等链路除外，参见下一节的“故障”列表）。因此，流量团队可以放心地迅速缓解影响。

  • 自动缓解灾难性的卫星节点故障。覆盖路由会自动把流量从故障卫星节点拉回核心集群；检测到异常波动时，卫星节点也会自行排空流量。

  • 卫星节点的退役／diskerase 流程运行得非常高效迅速，尽管此时它充当了“糊涂代理人”。

  • 该故障通过 OMG 迅速触发了 IMAG 响应，事实证明，这个工具很适合持续跟踪事件。跨团队响应非常出色，OMG 还进一步帮助所有人保持沟通。

做得不好的方面

故障

  • 流量管理服务器未对发送给 MDB 的命令执行适当的合理性检查。所有命令都应当幂等，或至少在重复调用时以安全方式失败。

  • MDB 没有拒绝所有权变更请求中缺少主机名约束的情况。

  • 退役工作流不会使用其他数据源（如计划中的机架退役）交叉核验退役请求。因此，请求销毁大量分布在不同地理位置的机器时，没有任何机制提出异议。

  • 退役工作流没有速率限制。机器一旦进入退役流程，磁盘擦除和其他退役步骤就会以最高速度执行。

  • 卫星节点停止服务、查询改由核心集群处理后，出口流量转移到不同位置，导致 Google 与外部网络之间的一些对等互联链路过载。在卫星节点恢复前，少数对等网络出现了短时拥塞，NST 也不得不开展相应的缓解工作。

恢复

  • 卫星节点机器的重装既缓慢又不可靠。重装使用 TFTP 传输数据，而对位于高延迟链路远端的卫星节点进行传输时，TFTP 表现很差。

  • 故障发生时，Autoreplacer 基础设施无法同时部署[值已隐去]台 GFE。为赶上自动部署速度，许多 SRE 必须并行进行手动部署。以下因素造成了自动化在初期速度缓慢：

    • 过于严格的 SSH 超时设置，使 Autoreplacer 无法在距离很远的卫星节点上可靠运行。

    • 无论机器是否已安装正确版本，都会执行缓慢的内核升级流程。

    • Autoreplacer 的并发回归缺陷导致每台工作机器最多只能运行两个机器部署任务。

    • 对 Autoreplacer 行为的理解混乱浪费了时间和精力。

  • 移除 23% 的目标时，监控配置增量安全检查（阈值为 25% 的变更）没有触发；重新添加相同内容时，由于这些内容占剩余目标的 29%，检查反而触发了。这使卫星节点监控的重新启用延迟了 30 分钟。

  • “安装程序”团队人手有限，因此变更既困难又缓慢。

  • 使用超级用户权限把机器从 diskerase 中强行夺回，留下了大量僵尸状态，造成持续的清理负担。

侥幸之处

  • 核心集群 GFE 与卫星节点 GFE 的管理方式截然不同，因此没有受到这场失控退役操作的影响。

  • 同样，YouTube CDN 作为独立基础设施运行，因此 YouTube 视频服务未受影响。若它也失效，故障会严重得多，持续时间也会更长。

术语表

管理服务器

一种 RPC 服务器，使自动化系统能够对前端服务基础设施执行特权操作。管理服务器最主要用于实现 PCR 以及集群启用／停用流程。

Autoreplacer

一种在机器之间迁移未纳入 Borg 管理的服务器的系统。它用于在机器故障时保持服务运行，也支持整体迁移和 colo 重新配置。

Borg

一种用于大规模管理任务和机器资源的集群管理系统。Borg 管理一个 Borg 单元中的全部机器，并把任务分配给尚有可用资源的机器。

退役（Decom）

decommissioning（退役）的缩写。设备退役是许多运维团队都会涉及的流程。

diskerase

生产硬盘离开 Google 数据中心之前，用于安全擦除硬盘的流程及相关软硬件系统。Diskerase 是退役工作流中的一个步骤。

GFE(Google前端)

外部世界访问几乎所有 Google 服务时所连接的服务器。

IMAG(Google事件管理)

一种为处理各类事件（从系统故障到自然灾害）建立标准一致方法，并组织有效响应的机制。

MDB(机器数据库)

一种存储 Google 机器资产状态等各类信息的系统。

OMG(Google的停机管理)

一个事件管理信息面板／工具，是跟踪和管理 Google 所有进行中事件的中心位置。

卫星

卫星节点是小型、廉价的机器机架，仅从 Google 网络边缘处理非视频前端流量。传统生产集群基础设施几乎都不适用于卫星节点。卫星节点不同于从 Google 网络边缘及互联网其他位置提供 YouTube 视频内容的 CDN；YouTube CDN 未受本次事件影响。

该复盘组织清晰，并对关键术语作了充分说明。例如：

简洁

该事件影响全球多个系统，因此复盘记录并分析了大量数据。聊天记录和系统日志等冗长数据源被提炼为摘要，未经编辑的版本则由正文链接。总体而言，这份复盘在详尽程度和可读性之间取得了平衡。

组织激励

理想情况下，高层领导应支持并鼓励有效的事后复盘。本节说明组织如何激励健康的复盘文化，指出文化失效的警示信号并提供解决办法，还会介绍用于简化和自动化复盘流程的工具与模板。

示范并贯彻无责行为

为正确支持事后复盘文化，工程领导者应始终示范无责行为，并在复盘讨论的每个环节鼓励无责原则。组织可以采用几项具体策略来贯彻这种行为。

使用无责语言

指责性语言会扼杀团队间的协作。请看以下情形：

Sandy 错过了 Foo 服务的一次培训，不确定如何运行某条更新命令。由此造成的延误最终延长了故障时间。

SRE Jesse［对 Sandy 的经理说］：“你是经理，为什么没有确保每个人都完成培训？”

这段话用了诱导式质问，会立刻让对方产生防御心理。更平衡的说法是：

SRE Jesse［对 Sandy 的经理说］：“读完复盘后，我发现值班人员错过了一项重要培训；参加过培训，本可以更快解决故障。或许应该要求团队成员完成这项培训后才能加入值班轮换？也可以提醒他们，一旦受阻就尽快升级。毕竟，升级并不是错，尤其是在它能减轻客户痛苦时！从长远看，我们其实不应过度依赖培训，因为人在紧张时刻很容易忘记所学内容。”

让所有事件参与者共同撰写事后复盘

如果事后复盘由某个人或某个团队闭门完成，就很容易漏掉导致故障的关键促成因素。

收集反馈

清晰的复盘评审流程和沟通计划，有助于防止指责性语言与观点在组织内扩散。建议的结构化评审流程见“事后复盘检查清单”一节。

奖励事后复盘成果

事后复盘若 写得好、后续行动得到落实并广泛分享，就能有效推动组织积极变革并防止故障重演。可以采用以下策略来激励事后复盘文化。

奖励行动项的完成

如果只奖励工程师撰写复盘，却不奖励完成相关行动项，就可能形成复盘和行动项迟迟无法收尾的恶性循环。应在撰写复盘与成功落实行动计划之间平衡激励。

奖励积极的组织变革

把事后复盘定位为扩大个人在组织内影响力的机会，可以激励各方广泛落实复盘所得的经验。可通过同事奖金、积极的绩效评价、晋升等方式奖励这种影响。

突出可靠性提升

长期来看，有效的复盘文化会减少故障并提高系统可靠性，团队因而可以专注于功能交付速度，而不是不断修补基础设施。在报告、演示和绩效评审中强调这些进步，本身就能激发动力。

将事后复盘负责人树立为领导者

通过邮件或会议庆祝复盘成果，或让作者向听众介绍经验教训，能够激励重视公开认可的人。把负责人树立为某类故障及其预防方面的“专家”，也能奖励许多寻求同事认可的工程师。例如，你可能听到有人说：“去找 Sara，她现在可是专家了。她刚合写了一份复盘，找出了如何补上那个缺口！”

游戏化

有些人会受到成就感和向更大目标推进的激励，例如修复系统弱点、提高可靠性。对他们而言，行动项计分板或燃尽图可以成为激励。Google 每年举行两次“FixIt”周，完成复盘行动项最多的 SRE 会获得小小的感谢礼物，当然也赢得夸耀的资本。图 10-3展示了一个复盘排行榜示例。

公开分享事后复盘

要在组织内维持健康的复盘文化，必须尽可能广泛地分享事后复盘。哪怕只采用以下一种做法，也会有所帮助。

在整个组织内发布通知

通过内部沟通渠道、电子邮件、Slack 等发布复盘草稿已可查看的通知。如果公司定期召开全员会议，可以形成惯例，每次分享一份近期值得关注的复盘。

开展跨团队评审

开展事后复盘跨团队评审。在评审中，一个团队回顾其事件经过，其他团队提出问题并从中间接学习。Google 的多个办公室设有向全体员工开放的非正式“事后复盘读书会”。

此外，由开发人员、SRE 和组织领导者组成的跨职能小组会评审整个复盘流程，并每月开会检查复盘流程和模板的有效性。

开展培训演练

培训新工程师时，可以使用“不幸之轮”：由一组工程师按照既往复盘中的角色重演事件，原事件指挥官也会参加，使演练体验尽可能接近“真实”。

每周报告事件与故障

编写每周故障报告，收录过去七天的事件与故障，并尽可能广泛地分享；再从每周故障中定期汇编并分享“精选事件”报告。

应对事后复盘文化失效

复盘文化的失效未必总是显而易见。以下是一些常见失效模式及建议的解决办法。

逃避关联

不再参与复盘流程，是组织复盘文化正在失效的信号。例如，假设 SRE 总监 Parker 无意间听到以下对话：

软件工程师 Sam：哇，你听说那次大故障了吗？

软件工程师 Riley：听说了，太糟了。他们现在肯定得写事后复盘。

软件工程师 Sam：天哪！幸好我没牵涉进去。

软件工程师 Riley：是啊，我可真不想参加讨论那次事故的会议。

确保对高关注度复盘中的指责性表述进行评审，有助于防止这种回避。分享高质量示例，并说明参与者如何得到奖励，也有助于让人们重新投入复盘流程。

未能巩固这种文化

高级管理人员使用指责性语言时，要作出回应并不容易。请看高层领导在一次故障会议上的这段话：

副总裁 Ash：我知道我们应该坚持无责原则，但这里是安全空间。肯定有人事先知道这是个坏主意，为什么你们没有听那个人的？

可以把叙事引向更具建设性的方向，以减轻这番话造成的伤害。例如：

SRE Dana：嗯，我相信每个人的出发点都是好的。为坚持无责原则，或许可以笼统地问：当时是否存在我们本可注意到的警示信号？我们又为什么可能忽略了它们？

人们会本着善意，根据当时可获得的最佳信息作出决定。调查误导性信息的来源，比追究责任对组织更有益。（如果你接触过敏捷原则，应该对此并不陌生。）

没有时间撰写事后复盘

高质量的事后复盘需要时间撰写。团队若被其他任务压得喘不过气，复盘质量就会下降。行动项不完整的低质量复盘会大幅提高事件重演的可能性。事后复盘是写给未来团队成员的信：必须始终坚持统一的质量标准，以免无意间给未来同事留下错误经验。应优先安排复盘工作，跟踪复盘的完成与评审，并给团队留出足够时间落实相关行动计划。“工具与模板”一节介绍的工具可以为这些活动提供帮助。

重复事件

如果团队经历了与以往事件相似的故障，就该深入挖掘原因。可以提出以下问题：

  • 行动项是否耗时过久、迟迟不能关闭？

  • 功能交付速度是否压过了可靠性修复？

  • 一开始记录的行动项是否正确？

  • 发生故障的服务是否早就应该重构？

  • 人们是否只是在用“创可贴”掩盖更严重的问题？

如果发现了系统性的流程或技术问题，就应退一步审视服务的整体健康状况。让每起相似事件的复盘协作者共同讨论防止再次发生的最佳行动方案。

工具与模板

一套工具和模板可以让复盘撰写及相关数据管理变得更容易，从而帮助组织启动复盘文化建设。Google 和其他公司提供了许多可用于此目的的资源。

事后复盘模板

模板让完整撰写并在组织内分享事后复盘变得更容易。标准格式也使领域外读者更容易理解复盘。你可以按需定制模板，例如记录团队特有的元数据：数据中心团队可能需要硬件品牌／型号，移动团队可能需要受影响的 Android 版本。随着团队成熟并能开展更复杂的复盘，还可以继续增加定制内容。

Google 的模板

Google 提供了 Google Docs 格式的事后复盘模板，地址为 http://g.co/SiteReliabilityWorkbookMaterials。我们内部主要使用 Docs 撰写复盘，因为共享编辑权限和评论便于协作。一些内部工具会预先填充元数据，降低撰写难度。我们还使用 Google Apps Script 自动完成部分编写工作，并把大量数据放入特定章节和表格，便于事后复盘库解析和分析。

事后复盘工具

截至本书写作时，Google 的复盘管理工具尚不对外提供（最新情况请查看我们的博客）。不过，我们可以说明这些工具如何促进复盘文化。

创建事后复盘

我们的事件管理工具会收集并存储大量有用的事件数据，并自动把数据写入事后复盘。例如：

  • 事件指挥官和其他角色

  • 详细的事件时间线和 IRC 日志

  • 受影响的服务和作为根因的服务

  • 事件严重性

  • 事件检测机制

事后复盘检查清单

为了帮助作者确保复盘得到妥善完成，我们提供了一份事后复盘检查清单，引导负责人完成关键步骤。下面只是清单中的几个检查示例：

  • 对事件影响进行全面评估。

  • 开展足够详细的根因分析，以指导行动项规划。

  • 确保行动项由服务的技术负责人审核和批准。

  • 与更广泛的组织共享事后复盘。

完整检查清单见 http://g.co/SiteReliabilityWorkbookMaterials。

存储事后复盘

我们把事后复盘存储在名为 Requiem 的工具中，方便任何 Google 员工查找。事件管理工具会自动把所有复盘推送到 Requiem，组织中的任何人也都能发布复盘供所有人查看。我们存储了数千份可追溯至 2009 年的复盘。Requiem 会从各份复盘中解析元数据，供搜索、分析和报告使用。

跟进事后复盘

事后复盘存储在 Requiem 数据库中，由此产生的行动项则作为缺陷录入集中式缺陷跟踪系统。因此，我们可以监控每份复盘行动项的关闭情况。借助这种跟踪能力，可以确保行动项不会被遗漏，以免服务变得越来越不稳定。图 10-4展示了工具所支持的复盘行动项监控模型。

事后复盘分析

复盘管理工具把信息存入数据库供分析。团队可以用这些数据编写复盘趋势报告，识别最脆弱的系统。这有助于发现原本可能被忽视的不稳定性根源或事件管理失灵。例如，图 10-5展示了分析工具生成的图表，其中包括各组织每月复盘数量、事件平均持续时间、检测用时、解决用时和影响范围等趋势。

结语

持续投入复盘文化建设，回报是更少的故障、更好的整体用户体验，以及依赖你的人的更多信任。始终如一地践行这些做法，会带来更好的系统设计、更短的停机时间，以及效率更高、更快乐的工程师。即使最坏的情况发生、事件再次出现，损害也会更小、恢复也会更快，并且还能获得更多数据，继续增强生产系统的韧性。
