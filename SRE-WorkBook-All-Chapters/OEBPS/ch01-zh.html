第 1 章　SRE 与 DevOps 的关系

class SRE implements interface DevOps——SRE 类实现 DevOps 接口

作者：Niall Richard Murphy、
Liz Fong-Jones 和 Betsy Beyer，
Todd Underwood、Laura Nolan
及 Dave Rensin 参与撰写

运维作为一门专业，很难做好。1如何把系统运行好，本身仍是一个普遍没有解决的问题；即使某些最佳实践确实已被证明有效，也高度依赖具体情境，远未得到广泛采用。此外，怎样把运维团队管理好，也基本无人给出答案。人们通常认为，对这些问题的系统研究始于运筹学：第二次世界大战期间，盟军曾用它改进流程与产出。但事实上，几千年来人类一直在思考如何把事情运作得更好。

然而，投入了如此多的努力与思考之后，可靠的生产运维依然难以实现，在信息技术和软件可运维性领域尤其如此。以企业界为例，运维常被当作成本中心，2这使得真正改善成果即使不是不可能，也极其困难。这种做法目光短浅得惊人，却尚未被广泛认识；不过，对它的不满已经催生了一场革命，改变了我们组织 IT 工作的方式。

这场革命源自解决一组常见问题的尝试。针对这些问题，最新的解决思路有两个不同的名字：DevOps 和站点可靠性工程（SRE）。人们往往分别谈论二者，仿佛它们是对上述企业思维模式完全不同的回应。3但我们希望让你相信：它们实际上的相似程度，以及两类实践者的共同之处，都远超你的想象。

不过，先来了解一下二者各自的核心原则。

DevOps 背景简介

DevOps 是一套较为宽泛的实践、指导原则和文化，旨在打破 IT 开发、运维、网络和安全领域之间的壁垒。由 John Willis、Damon Edwards 和 Jez Humble 总结的 CA(L)MS，是记忆 DevOps 哲学要点的实用缩写：文化（Culture）、自动化（Automation）、精益（Lean，指精益管理；另见持续交付）、度量（Measurement）和共享（Sharing）。共享与协作是这场运动的重中之重。采用 DevOps 时，你先改进某件事（通常通过自动化），再衡量结果，并与同事分享，让整个组织都能随之改进。支持性的文化有助于落实 CALMS 的每一项原则。

DevOps、敏捷以及其他各种业务与软件再造方法，都体现了同一种总体世界观：在现代社会中，怎样经营才最有效。DevOps 哲学中的各个要素很难彼此割裂，而这本来就是有意为之。不过，其中仍有几个关键观念可以相对独立地讨论。

不再各自为政

第一个关键观念是消除壁垒。这是对以下两种现象的回应：

  • 过去很流行、如今却日益显得过时的组织方式：运维团队与开发团队彼此分离

  • 大量事实表明，知识被严重割裂、只鼓励局部优化，以及缺乏协作，往往会直接损害业务4

事故是常态

第二个关键观念是：事故并不只是某个人孤立行为的结果，而是因为系统缺少应对必然会出错之时的防护措施。5例如，糟糕的界面会在压力下无意中诱导人做出错误操作；系统中某个设计缺陷会在某些未被明确说明的不利条件出现时让故障无可避免；失灵的监控则让人连系统是否出错都无从得知，更别说判断哪里出了错。一些观念较传统的企业，本能地想找出犯错者并加以惩罚。但这样做也有后果：最明显的是，它会鼓励人们混淆问题、隐瞒真相、相互推责，而这些最终都只是无益于利润的干扰。因此，与其试图杜绝事故，不如把重点放在加快恢复上，这样更有价值。

变更应当小步推进

第三个关键观念是：变更最好规模小、频率高。在某些环境中，变更委员会每月开会，讨论文档详尽的大型机配置变更计划；对这些环境而言，这种主张相当激进，但它并不新鲜。事实证明，让经验丰富的人审核所有变更，再把变更攒成批次以提高审核效率，几乎恰好与最佳实践背道而驰。变更确实有风险，但正确的应对方式，是尽可能把它拆成更小的组成部分。然后，把产品、设计和基础设施方面持续产生的变更汇成一条稳定、低风险的流水线。6这种策略再配合对小规模变更的自动测试，以及对不良变更的可靠回滚，就形成了持续集成（CI）和持续交付或部署（CD）等变更管理方法。

工具与文化相互影响

工具是 DevOps 的重要组成部分。尤其考虑到 DevOps 强调正确管理变更，而如今的变更管理要依赖高度专门化的工具，这一点就更加突出。但总体而言，DevOps 的倡导者坚信：采用新工作方式能否成功，关键在于组织文化，而非工具。良好的文化能够弥补工具的缺陷，反过来却很少成立。俗话说，文化能把战略当早餐吃掉。和运维一样，变革本身也很难。

度量至关重要

最后，在打破壁垒、处理事故等整体业务情境中，度量尤其关键。在每种情境下，都要通过客观度量确认实际发生了什么，验证局面是否正按预期改变，并为不同职能团队都能认可的讨论建立客观基础。（这一原则既适用于业务，也适用于值班等其他场景。）

SRE 背景简介

站点可靠性工程（SRE）这个名称及其对应的岗位，由 Google 工程副总裁 Ben Treynor Sloss 创立。7从上一节可以看到，DevOps 是一套宽泛的原则，关注运维与产品开发在整个生命周期中的协作。SRE 则既是一种岗位，也是一套被我们验证有效的实践（下文将介绍），还包含支撑这些实践的一些理念。如果把 DevOps 看成一种哲学和工作方法，那么可以说，SRE 落实了 DevOps 所描述的部分理念；与“DevOps 工程师”相比，它也更接近一个具体的工作或岗位定义。8所以从某种意义上说，class SRE implements interface DevOps，也就是“SRE 类实现了 DevOps 接口”。

DevOps 运动源于多家公司领导者与一线实践者之间的协作；与之不同，Google 的 SRE 在“SRE”一词广泛流行于全行业之前，就已经从公司整体环境中继承了大量文化。由于这段发展历程，SRE 这门学科目前在默认情况下不像 DevOps 那样把文化变革摆在最突出的位置。（当然，这并不意味着在任何一个具体组织中实施 SRE 时不需要文化变革。）

SRE 由以下具体原则来定义。

运维是一个软件问题

SRE 的基本信条是：要把运维做好，需要解决的是软件问题。因此，SRE 应当用软件工程方法来解决它。这里的视野非常宽广，既包括流程和业务变革，也包括同样复杂、但更传统的软件问题，例如重写整个技术栈，消除业务逻辑中的单点故障。

以服务等级目标（SLO）进行管理

SRE 并不试图让一切都达到 100% 可用。如我们的第一本书《站点可靠性工程》所述，出于多方面原因，这个目标并不正确。产品团队与 SRE 团队应当为服务及其用户群选择适当的可用性目标，再依照该 SLO 管理服务。9确定这样的目标，需要业务方深度参与协作。SLO 也具有文化层面的意义：它是利益相关方共同作出的决定；一旦违反 SLO，各团队便会在不追责个人的前提下重新审视方案。

努力减少琐务

对 SRE 而言，任何由系统结构决定、必须手工完成的运维任务都令人厌恶。（这并不是说我们没有这类运维工作；我们有很多，只是不喜欢它们。）我们相信，如果机器能够完成一项所需操作，那么通常就应当让机器来做。这种区分及其背后的价值取向在其他组织中并不常见；在那里，琐务就是工作本身，公司付钱雇人就是让其完成这些事。但在 Google 的 SRE 语境中，琐务不是本职工作，也绝不能成为本职工作。花在运维任务上的每一分钟，都无法用于项目工作；而我们正是通过项目工作，让服务变得更加可靠、更易扩展。

不过，依据“生产环境的智慧”，亲自执行运维任务确实能为决策提供至关重要的信息。这些工作让我们立足现实，因为它们会带来某个系统的实时反馈。琐务的来源必须能够识别，才能加以减少或消除。但如果运维工作量不足，也许反而应该更频繁地推出新功能和变更，让工程师持续熟悉所支持服务的运行方式。

生产环境的智慧

这里解释一下“生产环境的智慧”：我们所说的，是从某样东西实际运行于生产环境中获得的认识，也就是它实际如何表现、软件实际应如何设计等纷繁复杂的细节；它不是脱离现场事实、只在白板上推演出来的服务图景。你收到的每一次告警、团队接到的每一张工单等等，都是与现实的直接联系，都应当帮助我们改进系统的设计与行为。

用自动化消除今年的工作

这一领域真正的工作，在于判断哪些事情应该自动化、在什么条件下自动化，以及如何实现自动化。

Google 所实践的 SRE 对团队成员花在琐务上的时间设有硬性限制：琐务最多只能占工作时间的 50%，其余时间应用于能创造持久价值的工程工作。许多人把这个限制看成一道上限。其实，把它理解成一种保证更有用：它既是一项明确承诺，也是一套保障机制，确保人们以工程方法解决问题，而不是一遍又一遍地埋头做琐务。

当我们思考自动化与琐务时，这项基准在实际运作中会产生一种反直觉而有趣的相互作用。随着时间推移，SRE 团队最终会把某项服务中所有能自动化的工作都自动化，只剩下无法自动化的部分（即 Murphy-Beyer 效应）。在其他条件不变时，如果不采取别的措施，这些剩余工作会逐渐成为 SRE 团队工作的主体。在 Google，你通常要么继续增加所负责的服务，直到工作负载达到仍可保证 50% 工程时间的上限；要么自动化做得极其成功，于是可以彻底转去做别的事情。

降低失败成本，从而快速前进

引入 SRE 的主要收益之一，不一定是可靠性提高——当然，这确实会发生——而是产品开发产出得到改善。为什么？常见故障的平均修复时间（MTTR）缩短后，产品开发人员无需再浪费时间和精力收拾这些问题造成的残局，开发速度自然会提高。这也符合一个众所周知的事实：问题在产品生命周期中发现得越晚，修复成本就越高。SRE 的一项明确职责，就是改善这种过晚发现问题的不良状况，从而让整个公司受益。

与开发人员共同承担所有权

在“应用开发”和“生产运维”（有时也称程序员和运维人员）之间划出僵硬边界，会适得其反。如果职责分割和把运维归为成本中心的做法进一步造成权力失衡，或导致地位、薪酬不平等，问题就更加严重。

SRE 往往更关注生产问题而非业务逻辑问题，但他们用软件工程工具处理这些问题，因此与产品开发团队拥有许多共同技能。一般而言，SRE 在所负责服务的可用性、延迟、性能、效率、变更管理、监控、应急响应和容量规划方面具有专门知识。这些明确而具体的能力，正是 SRE 为产品及其开发团队提供的核心价值。10理想情况下，产品开发团队和 SRE 团队都应从整体上理解整个技术栈，包括前端、后端、库、存储、内核和物理机器；任何团队都不应把某个单独组件据为己有。事实证明，只要“模糊边界”，11让 SRE 也能为 JavaScript 添加监测手段，让产品开发人员也能验证内核是否合用，就可以完成更多工作：掌握变更方法并有权实施变更的人会大幅增加，各方也不再有动机把某项职能牢牢攥在自己手中。

在《站点可靠性工程》中，我们没有充分说明：在 Google，产品开发团队默认对自己的服务负有所有权。绝大多数服务既得不到 SRE 支持，也没有必要获得这种支持；不过，Google 仍会依据 SRE 原则管理所有服务。12当 SRE 团队与产品开发团队合作时，最终采用的同样是共同所有权模式。

无论职能或职称如何，都使用同一套工具

工具是影响行为的一个极其重要的决定因素。如果天真地认为 Google 的 SRE 之所以有效，与广泛开放的统一代码库、种类丰富的软件与系统工具、高度优化的专有生产技术栈等毫无关系，显然站不住脚。但我们与 DevOps 共享一项毫不含糊的信念：负责同一项服务的团队，13不论在组织中扮演什么角色，都应使用相同的工具。如果 SRE 用一套工具，产品开发人员用另一套，而且两套工具在不同情况下表现不一，甚至可能产生灾难性差异，就不可能把服务管理好。工具之间的差异越大，公司从每一次单项工具改进中获得的整体收益就越少。

异同对照

回顾上述原则，可以立即看出二者有许多共同点：

  • DevOps 和 SRE 都以接受“为了改进，变更不可或缺”为前提。若不接受这一点，就几乎没有腾挪空间。14

  • 协作是 DevOps 工作的核心。SRE 要有效运作，也离不开切实可行的共同所有权模式和良好的伙伴团队关系。和 DevOps 一样，SRE 在整个组织中也共享一套鲜明的价值观，这能稍稍降低团队打破壁垒的难度。

  • 变更管理最好通过持续的小步行动来进行，其中大多数变更最好既能自动测试，也能自动应用。变更与可靠性紧密相互影响，因此这一点对 SRE 尤其重要。

  • 合适的工具至关重要；在一定程度上，工具决定了你能够采取哪些行动。但我们不能过分关注某项目标是否通过某套特定工具实现。归根结底，用 API 管理系统是一种更重要的理念，其生命力会超过任何一种具体实现。

  • 度量是 DevOps 和 SRE 运作方式中绝对关键的一环。对 SRE 而言，SLO 主导着为改进服务而采取的行动。当然，没有度量就不可能建立 SLO；同时还需要跨团队讨论，最好有产品、基础设施或 SRE 以及业务方共同参与。对 DevOps 来说，度量常用于了解流程产出了什么、反馈循环持续多久，等等。无论把 DevOps 和 SRE 看作职业还是理念，二者都以数据为导向。

  • 管理生产服务的残酷现实是，坏事偶尔必然发生，而你必须讨论其原因。SRE 和 DevOps 都采用无责复盘，以抑制肾上腺素驱动、却于事无补的应激反应。

  • 归根结底，实施 DevOps 或 SRE 都是一项整体性工作；二者都希望通过一种高度明确的协作方式，让整个团队（或部门、组织）变得更好。无论 DevOps 还是 SRE，最终结果都应当是交付速度提升。15

可见，DevOps 和 SRE 有许多共同之处。

不过，二者也存在显著差异。从某种意义上说，DevOps 是一种范围更广的理念和文化。它带来的变化比 SRE 更广泛，因此也更依赖具体情境。至于如何在细节层面开展运维，DevOps 相对少有论述。例如，它并不规定服务具体应如何管理，而是选择把重点放在打破组织中更广泛的壁垒上。这一点很有价值。

相比之下，SRE 的职责定义较窄，其关注范围通常围绕服务和最终用户，而不是整个企业。因此，面对“怎样有效运行系统”这个问题，它会提出一套主张鲜明的思维框架，其中包括错误预算等概念。SRE 作为一种职业，虽然非常重视激励及其影响，却很少谈及孤岛化和信息壁垒等话题。它会支持 CI 和 CD，未必是因为二者有何商业理由，而是因为它们能够改进运维实践。换句话说，SRE 相信的事情与 DevOps 相同，只是理由略有不同。

组织环境与如何促成成功落地

DevOps 与 SRE 的运作方式在理念上高度重叠。不出所料，要让二者能够在组织内实施，并从实施中获得最大收益，所需条件也很相似。借用一句托尔斯泰差一点却并未真正说过的话：有效的运维方法都是相似的，失灵的方法却各有各的失灵之处。激励机制可以解释其中一部分原因。

如果一个组织的文化认可 DevOps 方法带来的收益，也愿意承担相应成本——通常包括招聘难度上升、维持团队与职责流动性所需的精力，以及为了吸引必然更稀缺的技能而增加的薪酬投入——那么，它还必须确保激励机制正确，才能充分获得这种方法的收益。

具体来说，在 DevOps 和 SRE 两种环境中，都应满足以下条件。

狭隘僵化的激励会限制成功

许多公司无意中制定了会损害集体绩效的正式激励机制。要避免这个错误，就不要让激励与发布结果或可靠性结果过度、狭隘地绑定。正如任何经济学家都会告诉你的，只要存在数字指标，人们就会找到办法钻指标的空子，造成不良后果；有时甚至完全出于善意。16相反，应让员工有自由寻找恰当的权衡。如前所述，DevOps 或 SRE 可以从整体上为产品团队提速，使软件组织的其他成员能够持续、可靠地向客户交付功能。这种机制还能解决传统系统团队与软件团队分立模式中一个长期存在的问题：设计与生产之间缺少反馈循环。如果 SRE 能尽早参与，最好在设计阶段就加入，那么无论最终由谁负责管理服务，系统部署到生产环境后的表现通常都会更好。（没有什么比丢失用户数据更能拖慢功能开发。）

自己动手修复，胜过归咎他人

此外，不要设置任何激励，让人把生产事故或系统故障的责任推给其他团队。从许多方面看，相互推责正是传统工程运维模式的核心问题：运维团队和软件团队彼此分离，便会各自产生不同的激励。要在组织层面抑制推责，可以考虑采用以下做法：

  • 当产品需要时，不仅要允许工程师修改代码和配置，还要主动鼓励他们这样做。同时，应授权这些团队在自身使命范围内大胆行动，从而消除促使他们放慢脚步的激励。

  • 支持无责复盘。17这样做可以消除淡化或掩盖问题的动机。要充分理解产品，真正优化其性能和功能，这一步至关重要；它依赖的正是前文所说的生产环境智慧。

应允许支持团队退出那些在运维上已经无可挽救的产品。撤回支持的可能性，会促使产品开发团队在获得支持前的准备阶段，以及产品已经获得支持之后修复问题，从而节省所有人的时间。究竟什么算“在运维上无可挽救”，会因具体环境而异；这里的互动应建立在双方都理解各自责任的基础上。向其他部门提出异议时，可以委婉地说：“我们认为，拥有这类技能的人才把时间用在别处，能创造更高价值。”也可以划清底线：“如果让这些人承担过多运维工作，却不给他们机会发挥工程技能，他们会辞职。”在 Google，彻底撤回对此类产品的支持已经成为制度化做法。

把可靠性工作视为专业岗位

在 Google，SRE 与产品开发分属不同组织。双方各有自己的关注点、优先事项和管理体系，谁也不必听命于对方。不过，当产品取得成功时，产品开发团队实际上会通过新增招聘名额，为 SRE 的扩张提供资源。这样一来，产品开发团队会关心 SRE 团队能否成功，正如 SRE 也会关心产品开发团队能否成功。SRE 还很幸运地得到了管理层高层的支持，因此工程团队即使反对以“SRE 方式”支持服务，异议通常也不会持续太久。不过，想用不同方式做事并不一定要调整组织结构图；只要形成一个采用不同实践的专业社群即可。

无论你是正式拆分组织结构，还是采用更非正式的机制，都必须认识到专业化会带来挑战。DevOps 和 SRE 实践者如果拥有一个由同行组成的实践社群，就能从中获得支持并促进职业发展；同时还需要有相应的职级体系，18对他们带来的独特技能与视角给予回报。

必须注意，Google 所采用的组织结构以及前述部分激励机制，在一定程度上依赖相当大的组织规模。例如，如果你的初创公司只有 20 人，也只有一个规模较小的产品，允许撤回运维支持就没多大意义。你仍然可以采用 DevOps 风格的方法，19但如果你唯一能做的就是帮助这个产品增长，那么改进一个运维表现糟糕的产品的能力就会受到削弱。不过通常来说，在满足增长需求和控制技术债务累积速度之间如何取舍，人们拥有的选择其实比自己想象的更多。20

“何时”可以代替“是否”

不过，当组织或产品增长到一定规模之后，你就有更大的余地决定支持哪些产品，或者如何安排支持工作的优先级。如果系统 X 显然会比系统 Y 更早得到支持，那么这种隐含的条件性，在 SRE 环境中可以发挥与决定不支持某项服务大致相同的作用。

在 Google，SRE 与产品开发之间牢固的伙伴关系已被证明极其重要。如果你的组织中也存在这种关系，那么是否撤回或提供支持，就可以依据不同产品运维特性的客观数据来决定，从而避免那些原本毫无成效的争论。

SRE 与产品开发之间富有成效的关系，还有助于避免一种组织反模式：产品开发团队被迫在产品或功能尚未真正就绪时就将其发布。SRE 可以改为与开发团队合作，先改善产品，再把维护负担从最有能力修复问题的人手中转移出去。

争取同等认可：职业与薪酬

最后，要确保促使人们做正确事情的职业激励已经到位：我们希望 DevOps/SRE 组织得到与产品开发团队同等的认可。因此，各团队成员应当接受大致相同方式的评价，并获得同等的经济激励。

结语

从许多方面看，在 IT 运维这片整体版图中，DevOps 与 SRE 无论在实践还是理念上都十分接近。

要取得实质性进展，DevOps 和 SRE 都需要充分讨论、管理层支持，以及实际工作者的认同。实施任何一种方法都是一段旅程，不是速效药；“只改名、再问责”的做法21徒有其表，不太可能带来收益。SRE 对如何开展运维有更明确的主张，因此在这段旅程的早期，会提出更多改变工作实践的具体建议，尽管这些建议需要结合实际情况调整。DevOps 关注面更广，因此理解起来更困难，也更难转化为具体步骤；但恰恰因为范围广，它在初期遭遇的阻力可能更小。

不过，二者的实践者使用许多相同的工具，采用相同的变更管理方法，也共享依据数据决策的思维方式。归根结底，不论我们叫什么名字，面对的都是同一个长期存在的问题：生产环境，以及如何把它变得更好。
