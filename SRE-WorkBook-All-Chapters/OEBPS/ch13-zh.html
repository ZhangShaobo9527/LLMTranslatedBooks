第 13 章　数据处理流水线

作者：Rita Sodt 和 Igor Maravić（Spotify），Gary Luo、Gary O’Connor 和 Kate Ward 参与撰写

数据处理是一个复杂且持续演进的领域，需要应对规模越来越大的数据集、计算密集型的数据转换，以及对快速、可靠、低成本结果的需求。如今的数据来自各种渠道，从移动端使用统计、集成式传感器网络到 Web 应用日志，不一而足。数据处理流水线能够把这些往往没有边界、缺乏顺序且规模遍及全球的数据集，转化为结构化、带索引的存储，从而为关键业务决策提供依据，或支持新的产品功能。数据处理不仅能揭示系统与用户行为，往往还直接关系到核心业务。流水线中的数据一旦延迟或出错，就可能演变为用户可见的问题，而修复这类问题通常成本高、耗费人力且旷日持久。

本章首先结合产品示例，介绍大数据处理流水线的几类常见应用。随后讨论如何确定流水线需求、选择设计模式，并总结贯穿开发生命周期的管理最佳实践。我们还会介绍优化流水线时可做的权衡，以及衡量流水线健康状况关键信号的方法。服务上线后若要持续健康、可靠地运行，SRE 和开发人员都应掌握这些工作。理想情况下，SRE 应从早期就参与其中：Google 的 SRE 团队会定期为数据处理流水线开发团队提供咨询，确保流水线能够顺利发布、修改和运行，而不会给客户带来问题。

最后，Spotify 案例研究将概述其事件投递处理流水线。该流水线综合使用内部系统、Google Cloud 和其他第三方解决方案，承担复杂且至关重要的业务数据处理。无论您直接负责流水线，还是负责依赖流水线产出数据的其他服务，都可以借助本章内容提高流水线乃至服务的可靠性。

如需全面了解 Google 在数据处理流水线方面的理念，请参阅我们的第一本 SRE 图书第 25 章。

流水线应用

流水线应用种类繁多，各有优势和适用场景。一条流水线可以包含多个阶段，每个阶段都是依赖其他阶段的独立处理过程；高层规范会将这些阶段抽象起来。以 Cloud Dataflow 为例，用户通过较高层的 API 编写业务逻辑，流水线技术再把它转换成一系列前后衔接的步骤或阶段，前一阶段的输出成为后一阶段的输入。下面介绍几类流水线应用及其适用场景，并通过两家需求和实现方式不同的示例公司，说明如何根据具体用例确定项目目标，进而选择最合适的数据流水线。

通过事件处理和数据转换整理数据

提取、转换、加载（ETL）是数据处理中的常见范式：先从源中提取数据，对数据进行转换并视需要做反规范化，再以专用格式“重新加载”。在较新的应用中，这一过程可能类似认知流程：先从某种传感器获取实时或回放数据，经过筛选和编排，再“训练”专用数据结构，例如机器学习网络。

ETL 流水线的工作方式与此类似：从一个或多个来源提取数据，完成转换，再加载或写入另一个数据源。转换阶段可服务于多种用途，例如：

  • 更改数据格式以添加或删除字段

  • 跨数据源执行聚合计算

  • 为数据建立索引，使使用这些数据的服务作业获得更好的查询特性

通常，ETL流水线会准备数据以进行进一步分析或提供服务。如果使用正确，ETL流水线可以执行复杂的数据操作，并最终提高系统效率。ETL流水线的一些示例包括：

  • 机器学习或商业智能用例的预处理步骤

  • 计算，例如计算给定事件类型在特定时间间隔内发生了多少次

  • 计算和准备账单报告

  • 为Google 的网络搜索提供支持的索引流水线

数据分析

商业智能是指收集、整合、分析和呈现大量信息所用的技术、工具与实践，目的是支持更好的决策。无论产品是零售业务、手机游戏还是联网的物联网传感器，汇总多个用户或设备的数据，都有助于判断哪些环节出了问题、哪些环节运行良好。1

为说明数据分析场景，假设一家虚构公司刚推出手机和网页游戏《Shave the Yak》。公司希望了解用户如何在移动端和网页端与游戏交互，于是先生成处理玩家事件数据的分析报告。业务负责人要求每月报告最常用的游戏功能，以便规划新功能并开展市场分析。游戏的移动端和网页端分析数据存放在 Google Cloud BigQuery 表中，由 Google Analytics 每天更新三次。团队配置了一个作业，每当表中加入新数据便运行；作业完成后，会向公司的每日汇总表写入一条记录。

机器学习

机器学习（ML）应用用途广泛，例如辅助癌症预测、识别垃圾邮件，以及为用户提供个性化商品推荐。典型的机器学习系统包含以下阶段：

  1. 从较大的数据集中提取数据特征及其标签。

  2. ML算法在提取的特征上训练模型。

  3. 在测试数据集上评估模型。

  4. 部署模型，使其他服务能够调用它。

  5. 其他系统使用模型提供的响应来做出决策。

为了展示机器学习流水线的实际运行方式，假设 Dressy 是一家在线服装零售商。公司希望通过有针对性的推荐提高收入。新商品上传后，系统应在 12 小时内把它纳入用户推荐；最终目标则是在用户浏览网站和评价服装时提供近实时推荐。作为推荐系统建设的第一步，Dressy 考察了以下方法：

协作

显示彼此相似的产品。

聚类

显示相似用户喜欢的产品。

基于内容

显示与用户浏览或喜欢的其他产品相似的产品。

Dressy 拥有用户资料和评价数据，因此选择聚类过滤。新上传的商品没有结构化数据或统一标签，例如不同供应商可能用不同类别和格式描述颜色、尺码和服装特征。因此，团队需要建立流水线，把商品信息与用户资料数据联结起来，并预处理为 TensorFlow 可用的格式。机器学习系统包含多条流水线，负责预处理训练模型所需的多源数据。Dressy 开发团队利用这些训练数据创建 TensorFlow 模型，为客户提供适当的推荐。图 13-1 展示了完整方案，后文逐步说明。

  1. 开发团队选择使用 Google Cloud Dataflow 流式流水线，把图像发送给图像分类服务；该服务返回特征列表，从而将数据预处理为带标签的服装数据。

  2. 团队预处理多个来源的数据，用于训练一个能够返回五件最相似服装的模型。该工作流根据商品数据以及 BigQuery 客户资料中的购买历史生成机器学习模型。

  3. 他们使用流式 Dataflow 流水线，把数据预处理为客户个性化资料。这些资料作为训练 TensorFlow 模型的输入，训练后的模型二进制文件存放在 Google Cloud Storage（GCS）存储桶中。模型进入生产环境前，团队会用预处理后的模型评估测试集检查其准确性。

  4. 推荐服务为指定客户返回推荐结果，供 Web 和移动端前端使用。团队采用 TensorFlow 和 Cloud ML 在线预测服务。

  5. 面向客户的购物前端根据预测服务提供的最新服装推荐向用户展示内容。

Dressy 发现，新模型有时超过 24 小时仍未发布，推荐功能也会间歇性报错。这是首次部署新模型时常见的问题，但可通过一些简单步骤排查。如果决策、分类或推荐没有呈现，或者结果过时、不正确，应检查以下问题：

  • 数据是否堵在流水线入口，因而尚未得到预处理并用于训练模型？

  • 模型质量不佳是否由软件缺陷、垃圾数据过多或训练特征选择不当造成？

  • 最近是否生成了ML模型的新版本，或者该模型的过时版本正在生产中运行？

所幸 Dressy 配备了一组监控和检测工具，能够在客户受影响前发现问题；发生故障时，这些工具也能帮助团队迅速修复或回滚有问题的代码。有关监控与告警实现的详情，请参阅第 4 章。

流水线最佳实践

以下最佳实践适用于以服务方式运行的流水线，也就是必须及时、正确地处理数据，供其他系统使用的流水线。要把流水线妥善部署为服务，需要完成一系列工作：用 SLO 定义并衡量客户需求，从容应对性能下降和故障，编写文档，并建立能在问题进入生产环境前将其发现的开发生命周期。

定义并衡量服务等级目标

应当自动检测流水线何时处于异常状态，以及是否未能满足客户需求。在可能耗尽错误预算时收到通知，有助于尽量减小客户影响（错误预算详见第 2 章）；同时也要在可靠性与功能发布之间取得合理平衡，因为客户两者都关心。本节余下部分将给出流水线 SLO 及其维护方式的示例。

数据新鲜度

流水线的数据新鲜度 SLO 通常采用以下几种形式：

  • X% 的数据在 Y 秒、分钟或天内处理完毕。

  • 最旧数据的延迟不超过 Y 秒、分钟或天。

  • 流水线作业在 Y 秒、分钟或天内成功完成。

例如，《Shave the Yak》手机游戏可以设定这样的 SLO：影响用户分数的所有操作中，99% 必须在 30 分钟内反映到计分板上。

数据正确性

创建SLO以确保数据正确性可确保在流水线中收到潜在数据错误的警报。例如，计费流水线中的正确性错误可能导致向客户收取过多或过少的费用。正确性目标可能很难衡量，尤其是在没有预定义的正确输出的情况下。如果您无权访问此类数据，则可以生成它。例如，使用测试账户来计算预期的输出。一旦有了这些"黄金数据"，就可以比较预期和实际输出。从那里，您可以创建对错误/差异的监控，并在测试数据流经实际生产系统时实施基于阈值的警报。

另一个数据正确性SLO涉及向后分析。例如，您可以设置一个目标，即每季度不超过0.1%的发票不正确。您可以为从流水线输出数据提供错误数据或错误的小时/天数设置另一个SLO目标。数据正确性的概念因产品和应用而异。

数据隔离与负载均衡

有些数据分区优先级更高，或处理时需要更多资源。如果对高优先级数据承诺了更严格的 SLO，就必须确保资源紧张时先处理这些数据。具体实现因流水线而异，常见方式是在任务系统中使用不同队列或不同作业，并让工作器领取当前优先级最高的任务。还可以用不同的内存、CPU 或网络层级配置运行多组流水线应用或工作器；低配置工作器处理失败的任务，可在更高配置的工作器上重试。当资源或系统受限、无法迅速处理全部数据时，这种隔离机制能够保证高优先级项目先于低优先级项目得到处理。

端到端衡量

如果流水线包含一系列阶段，很容易让人想为每个阶段或组件分别设定 SLO。但这种衡量方式既不能反映客户体验，也不能体现系统的端到端健康状况。以 Google Analytics 一类事件流水线为例，端到端 SLO 涵盖日志输入采集，以及数据进入可供服务状态前的所有处理步骤。虽然可以分别监控每个阶段并为其设定 SLO，但客户关心的是所有阶段合计后的结果。逐阶段衡量还会迫使您收紧各组件的告警阈值，产生更多无法代表用户体验的告警。

此外，只逐阶段衡量数据正确性，可能漏掉端到端的数据损坏问题。例如，各阶段都报告正常，但某个上游阶段新增了一个它认为下游会处理的字段，并假定附加数据最终会用于响应用户请求；下游作业并不认识该字段，于是将数据丢弃。两个作业都认为自己行为正确，用户却看不到数据。

为依赖项故障做好准备

定义 SLO 后，应确认自身不会过度依赖其他产品的 SLO 或 SLA，尤其是这些产品可能无法兑现承诺时。许多产品（如 Google Cloud Platform）会在网站公布 SLA。识别第三方依赖后，至少要按照其 SLA 所涵盖的最大故障范围进行设计。例如，从 Cloud Storage 读写数据的流水线所有者在定义 SLO 时，应核实其公布的可用时间和保证是否合适。若单区域可用性保证不足以让流水线满足数据处理时限 SLO，可跨区域复制数据以获得更高可用性。

当服务提供商的基础设施未达到其 SLA 时，依赖它的流水线会受到负面影响。如果您的流水线要求比提供商公布的保证更严格，那么即使提供商仍处于 SLA 允许范围内，您的服务也可能失败。现实地规划依赖故障，有时意味着接受较低的可靠性，并向客户提供较宽松的 SLA。2

在 Google，为了促使团队在开发流水线时考虑依赖故障，我们会安排计划内停机。例如，许多流水线依赖其所在数据中心的可用性；灾难恢复测试（DiRT）会模拟区域故障。预先设计了故障处理机制的流水线会自动切换到其他区域；其余流水线则会延迟，直到监控通知操作人员并由其手动切换。手动故障转移成功的前提，是流水线能在另一地区取得足够资源来启动生产栈。最好的情况下，失败的手动切换只是延长故障；最坏的情况下，处理作业可能继续使用陈旧数据，向下游引入过时或错误的数据。恢复方式取决于系统设计。例如，若正确数据被错误数据覆盖，就可能需要从旧备份恢复，并重新处理所有缺失数据。

总而言之，良好的做法是为您所依赖的系统不可用的那一天做好准备。即使是最好的产品也会失败，并遭受中断。定期练习灾难恢复方案，以确保您的系统能够应对常见和罕见的故障。衡量您的依赖关系并尽可能自动执行系统响应。

创建并维护流水线文档

如果编写和维护得当，系统文档可以帮助工程师可视化数据流水线及其依赖项，了解复杂的系统任务，并有可能缩短停机时间。我们建议您的流水线使用三类文档。

系统图

图 13-2 所示的系统图可以帮助值班工程师迅速定位潜在故障点。在 Google，我们鼓励团队绘制系统图，标明流水线应用、数据存储等每个组件，以及各步骤执行的转换。图中的每个组件和转换都可能卡住，使数据停止流动；每个组件也可能引入影响数据正确性的软件缺陷或应用配置错误。

系统图应包含指向不同流水线阶段的其他监控和调试信息的快速链接。理想情况下，这些链接应从实时监控信息中提取，以显示每个阶段的当前状态（例如，等待相关作业完成/处理/完成)。显示历史运行时信息还可以指示流水线阶段花费的时间是否比预期的长。这种延迟可能预示性能下降或中断。

最后，即使在复杂的系统中，系统图也使开发人员可以更轻松地分析功能启动期间应了解的数据依赖性。

流程文档

重要的是记录如何执行常见任务，例如发布新版本的流水线或对数据格式进行更改。理想情况下，您还应该记录一些不太常见(通常是手动)的任务，例如在新区域中进行初始服务启动或最终服务关闭。记录完任务后，请调查将所有手动工作自动化的可能性。如果任务和系统是自动化的，请考虑直接从源代码生成文档，以便使两者保持同步。

操作手册条目

系统中的每个告警条件都应有对应的操作手册条目，说明恢复步骤。在 Google，我们发现，在发给值班工程师的告警消息中附上该文档的链接非常有用。我们的第一本书第 11 章详细讨论了操作手册条目。

梳理开发生命周期

如图13-3所示，流水线的开发生命周期(或对流水线的更改)与其他系统的开发生命周期没有太大差异。本节遵循流水线开发各个阶段的典型发布流程生命周期。

原型设计

开发的第一阶段是制作流水线原型并验证语义，确认所选方案能够表达执行流水线所需的业务逻辑。某种编程语言可能更适合表达业务逻辑，或更容易与现有库集成；某种编程模型也可能更契合具体用例，例如 Dataflow 与 MapReduce、批处理与流式处理。完整比较示例参见博客文章“Dataflow/Beam & Spark：编程模型比较”。若要给现有流水线增加功能，建议在原型阶段加入代码并运行单元测试。

使用 1% 数据试运行

完成原型后，使用生产数据在整个堆栈上运行一个小的设置会很有帮助。例如，使用实验集运行流水线，或者在非生产环境中使用1%的生产数据空运行。逐步扩大规模，跟踪您的流水线性能，以确保您不会遇到任何瓶颈。产品发布给客户后，请运行性能测试。这些测试是不可或缺的开发步骤，有助于防止因推出新功能而造成停机。

预发布环境

在部署到生产之前，在预生产(或演练)环境中运行系统很有用。预发布环境中的数据应尽可能接近实际生产数据。我们建议保留生产数据的完整副本或至少有代表性的子集。单元测试不能解决所有流水线问题，因此让数据端到端流经系统以解决集成问题非常重要。

集成测试还可以识别错误。使用单元测试和集成测试，对新生成的数据与先前生成的已知正常数据进行A/B比较。例如，在对发行版进行认证并将其标记为可以投入生产之前，请检查您的先前发行版是否存在预期或意外的差异。

金丝雀发布

流水线会持久化数据，而且转换通常很复杂，因此测试和验证比无状态作业更费时，也需要更谨慎。生产版本一旦出错，应尽早发现以限制影响，金丝雀发布正可用于此目的：它只部署部分服务（此处为流水线应用）并监控结果，详见第 16 章。金丝雀应覆盖整条流水线，而非单个进程。金丝雀阶段可以处理与在线流水线相同的真实生产数据，但不写入生产存储；两阶段变更等技术也能发挥作用。通常必须等整个处理流程结束后，才能发现影响客户的问题。试运行或两阶段变更完成后，应比较金丝雀流水线与在线流水线的结果，以确认运行状况并检查数据差异。

有时可以通过逐步更新作业的任务或先在一个区域中然后在另一个区域中进行更新来在金丝雀中前进，但这并不总是通过流水线实现。使用复制数据的流水线（例如Dataproc 和Dataflow, )支持区域终结点 ，并防止这种金丝雀般的进展-您无法隔离地重新加载一个单元。如果您运行多地部署流水线，则可能无法像执行服务作业一样将其部署到单个区域(或一定百分比的服务器)。而是先对一小部分数据执行转储，或者如前所述，先在空运行模式下转储。345

在验证金丝雀或生产前环境期间，重要的是衡量流水线的运行状况。通常，您可以使用与跟踪SLO相同的指标。验证金丝雀是一项很适合自动化的任务。

执行部分部署

除了取消更改之外，您可能还希望执行部分部署，尤其是在存在主要功能启动或更改会影响系统性能和资源使用的情况下。如果不先对实际流量的子集测试更改，就很难预测这些发布的影响。您可以在接受允许的数据子集的流水线中将部分部署实现为标志或配置选项。考虑首先处理一个或两个账户的新功能，然后逐渐增加数据量（例如，样本数据的〜1%，〜10%，〜50%，最后是100%)。

部分部署可能会以多种方式出错：输入数据可能不正确或被延迟，数据处理可能存在错误，或者最终存储可能存在错误。这些问题中的任何一个都可能导致中断。避免将一组损坏的数据推广到您的低延迟前端。力争在用户遇到问题之前尽早发现这些类型的问题。

部署到生产环境

在将新的流水线二进制文件和/或配置完全推广到生产环境之后，您应该有足够的信心确信您已经审查了任何潜在的问题(如果确实发生了问题，则监控将向你告警)。如果您的部署出错，则能够从已知的良好状态快速还原（例如，回滚二进制文件)，并将任何可能损坏的数据标记为不良数据（例如，将不良数据替换为先前备份版本中的数据，请确保没有作业读取受影响的数据，和/或在必要时重新处理数据)。

减少热点和不良工作负载模式

热点是指资源因访问过于集中而过载，继而导致操作失败。流水线容易受到读写工作负载模式的影响，使局部数据区域出现延迟。常见热点包括：

  • 由于多个流水线工作器正在访问一个服务任务而引发错误，从而导致过载。

  • 由于并发访问仅在一台计算机上可用的一条数据，导致CPU耗尽。通常，数据存储的内部组件具有最低级别的粒度，如果进行大量访问，粒度可能会变得不可用（例如， Spanner数位板 可能由于有问题的数据段而变得超载)即使大多数数据存储都可以)。

  • 由于数据库中行级锁争用而导致的延迟。

  • 由于同时访问硬盘驱动器而导致的延迟，这超出了驱动器磁头足够快地移动以快速定位数据的物理能力。在这种情况下，请考虑使用固态驱动器。

  • 需要大量资源的大型工作单元。

热点可以局限于一部分数据。为避免整条流水线被拖住，可以阻塞单条记录等细粒度数据，让其余流水线继续推进；基础设施通常能够提供这种能力。若某块处理工作消耗了不成比例的资源，流水线框架可以把工作拆小并动态再均衡。为稳妥起见，还应在客户端逻辑中设置紧急停止机制，以便暂停处理并隔离资源消耗过大或反复出错的细粒度工作。例如，应能迅速设置标志或下发配置，跳过符合某种模式或属于问题用户的输入数据。

降低热点风险还可以采用以下策略：

  • 重组数据或访问模式以平均分散负载

  • 减少负载（例如，静态分配部分或全部数据)

  • 减少锁粒度以避免数据锁争用

实施自动扩缩容与资源规划

工作负载突增很常见，准备不足就可能导致服务故障。自动扩缩容可以帮助处理峰值，使系统不必 100% 的时间都按峰值负载配置资源（详见第 11 章）。持续运行满足峰值容量所需的全部工作器既昂贵又低效；自动扩缩容可以缩减空闲工作器，避免为不需要的资源付费。这对负载变化明显的流式流水线尤其重要。多个批处理流水线可能同时运行，并消耗全部可用资源。

预测系统的未来增长并相应地分配容量可确保您的服务不会耗尽资源。权衡资源成本和使流水线更高效所需的工程量也很重要。在进行资源规划并估算未来的增长时，请记住，成本可能不会仅仅与运行流水线作业隔离开来。您还可能要支付数据存储和网络带宽成本，以便跨区域或跨区域的读写操作复制数据。另外，某些数据存储系统比其他系统昂贵。即使单位存储成本很低，这些成本也可以迅速增加，以用于非常大的数据集或使用存储服务器上大量计算资源的昂贵数据访问模式。良好做法是通过定期检查数据集并修剪未使用的内容来帮助降低成本。

尽管应根据其端到端SLO衡量一系列流水线阶段的有效性，但应在每个单独阶段对流水线效率和资源使用情况进行度量。例如，假设您有许多使用BigQuery的工作，并且注意到发布后BigQuery资源使用量显着增加。如果您可以快速确定哪些工作是造成负担的，则可以将工程重点放在这些工作上以降低成本。

遵守访问控制与安全策略

数据流经您的系统，并且通常会一路被持久化。在管理任何持久数据时，我们建议您遵循以下隐私，安全性和数据完整性原则：

  • 避免将个人身份信息(PII)存储在临时存储桶中。如果需要临时存储PII，请确保数据已正确加密。

  • 限制对数据的访问。仅授予每个流水线阶段所需的最小访问权限，以读取上一个阶段的输出数据。

  • 对日志和PII设置生存时间(TTL)限制。

以绑定到某个 GCP 项目的 BigQuery 实例为例，其访问权限可通过 Google Cloud Identity and Access Management 管理。按功能分别创建项目和实例，可以用更细粒度的范围限制访问。表可归属于主项目，并在客户端项目中交叉创建视图，以提供受控访问。例如，Dressy 只允许具有特定项目角色的作业访问含敏感客户信息的表。

规划故障升级路径

流水线应具备足够韧性，使机器或区域故障不会直接触发违反 SLO 的寻呼。收到寻呼时，意味着自动化措施已经用尽，需要人工介入。如果 SLO 定义清晰，指标、告警和检测机制可靠，您应能在客户察觉或报告问题前收到通知。一旦违反 SLO，必须快速响应，并主动与客户沟通。

检查点机制

流水线通常是长时间运行的进程，会分析或修改大量数据。若未专门处理，提前终止会丢失状态，迫使整条流水线重新执行；创建 AI 模型的流水线尤其如此，因为每轮模型计算都依赖先前结果。检查点是一种让流水线等长时间运行进程定期把部分状态保存到存储中的技术，以便日后从该状态恢复。

检查点常用于故障恢复，但作业需要被抢占或重新调度时也很有用，例如调整 CPU 或 RAM 限制。作业可以安全关闭，并在重新调度后识别已处理的工作单元。由于流水线已知哪些工作已经完成，检查点还能帮助跳过代价高昂的读取或计算。

代码模式

一些常见的代码模式可以使您的流水线更有效地管理并减少进行更改或更新所需的工作。

复用代码

如果您操作多个相似的流水线并希望实施新的监控功能或指标，则必须对每个单独的系统进行检测。如果使用正确的策略，则这种通用的工作流程并不困难。实施可重用的代码库使您可以在一个位置添加用于监控的度量，并在多个流水线或阶段之间共享它。共享库使您能够：

  • 以标准方式获得对所有数据流水线的洞察力。

  • 为每个流水线重用其他数据分析系统（例如，适用于所有流水线的流量报告)。

  • 针对多个作业在同一度量上发出警报，例如通用数据新鲜度告警。

以微服务方式构建流水线

使用微服务时，让服务执行一项任务并做好它很重要。与使用许多核心服务相比，使用一组相同的核心库(仅在业务逻辑上有所不同)的微服务的操作要容易得多。类似的模式可以应用于流水线。与其创建一个整体式流水线应用，不如创建可以分别发布和监控的较小的流水线。这样，您将获得与从微服务架构中获得的相同的收益。

流水线故障：预防与响应

流水线可能因多种原因失败，最常见的是数据延迟和数据损坏。发生故障时，迅速定位并修复问题能显著降低影响。在 Google，每当发生故障或违反 SLO，我们都会跟踪平均检测时间（MTTD）和平均修复时间（MTTR），以衡量发现和修复问题的效率。事后分析还会追查故障原因、归纳模式并消除运维琐事的来源。

本节介绍一些常见的故障模式，有效响应流水线故障的方法，以及有助于您防止将来发生流水线故障的策略。

潜在故障模式

数据延迟

流水线的输入或输出延迟都可能导致故障。若缺少适当防护，下游作业可能在必需数据尚未到齐时就开始运行。陈旧数据几乎总比错误数据好；若流水线处理不完整或损坏的数据，错误会向下游传播，而恢复或重处理坏数据会耗费时间、延长故障。相反，让流水线暂停并等待数据，在数据可用后再恢复处理，能够保持数据质量。因此，必须建立所有阶段都会遵守的数据依赖关系。

数据延迟的影响随流水线类型而异，可能只是应用数据过时，也可能使整条流水线停滞。在批处理流水线中，每个阶段都要等待前一阶段完成后再启动。流式系统更灵活：借助 Dataflow 等基于事件时间的处理方式，只要对应的上游部分完成，下游阶段即可立即处理相应部分，不必等待所有上游工作全部结束。

发生此类中断时，您可能需要通知任何相关服务。如果停机是用户可见的，则可能还必须通知客户。在调试流水线中断时，查看当前和过去流水线运行的进度以及直接链接到日志文件和数据流图非常有帮助。能够在分析系统的计数器和统计信息时跟踪整个系统的工作单元也很有用。

数据损坏

若未被发现，流水线中损坏的输入或输出数据会造成用户可见的问题。应设置测试来识别损坏数据，并用检测逻辑对潜在损坏发出告警，从而避免许多用户影响。例如，流水线系统可以实施阻断策略和滥用或垃圾数据检测，自动或手动过滤不良数据源。

损坏的数据可能有多种原因：软件错误，数据不兼容，不可用的区域，配置错误等。修复损坏的数据涉及两个主要步骤：

  1. 通过防止进一步的损坏数据进入系统来减轻影响。

  2. 从以前的已知正确版本还原数据，或重新处理以修复数据。

如果单个区域正在提供损坏数据，可能需要把在线服务作业和数据处理从该区域排空。若根因是软件或配置缺陷，应迅速回滚相关二进制文件。数据损坏往往会造成某个时间窗口的数据错误；修复根因后还必须重新处理这些数据。为降低成本，可选择性地只读取和处理受影响的用户或账户信息；也可以持久化部分中间数据作为检查点，避免从头到尾重跑整条流水线。

如果流水线的输出损坏，则下游作业可能会传播损坏的数据，或者正在服务的作业可能会提供不正确的数据。即使进行了最佳测试，开发 修改和发布实践，软件或配置错误可能会导致数据损坏。我们建议您为这种情况做准备，并能够快速重新处理和还原数据。从这种数据损坏中恢复是劳动密集型的并且难以自动化。

潜在原因

流水线依赖项

当您尝试确定中断的原因时，调查流水线依赖项（例如存储，网络系统或其他服务)很有用。这些依赖关系可能会限制您的请求/流量，或者，如果资源不足，它们会拒绝任何新数据。输入/输出的速率可能会由于多种原因而变慢：

  • 输出接收器或存储设备可能拒绝写入数据。

  • 可能存在无法完成的特定热点数据范围。

  • 可能存在存储错误。

一些流水线依赖问题无法解决。提交故障单或错误，并留出足够的时间来添加更多资源或解决流量模式，这一点很重要。实施负载均衡并删除低优先级数据可能有助于减轻影响。

流水线应用或配置

流水线故障可能是瓶颈，流水线作业中的错误或配置本身中的错误（例如，CPU密集型处理，性能回归，内存不足故障，易于出现热点的滥用数据，或指向错误的输入/输出位置的配置)。根据原因，有几种可能的解决方案：

  • 回退二进制文件/配置，选择修补程序，或修复任何权限问题。

  • 考虑重组导致问题的数据。

应用或配置错误可能会导致数据不正确或导致数据延迟。这些类型的错误是最常见的中断原因。我们建议您花一些时间进行流水线开发，并确保新的二进制文件和配置在非生产环境中正常运行，然后再进行全面部署。

资源意外增长

系统负载的突然变化和计划外变化可能会导致流水线发生故障。您可能需要其他计划外资源，以保持服务运行。自动扩缩容 您的应用作业可以帮助满足新负载的需求，但是您还应该意识到，增加的流水线负载也会给下游依赖性带来压力-您可能还需要计划更多的存储和/或网络资源。

良好的资源规划和准确的增长预测可以在这些情况下提供帮助，但是这种预测可能并不总是正确的。我们建议您熟悉请求其他紧急资源的过程。根据流水线部署的性质和所需的资源数量，获取这些资源所需的时间可能很长。因此，我们建议准备临时解决方案以保持您的服务正常运行-例如，通过流水线优先处理不同类别的数据。

区域级故障

区域故障对所有流水线都有害，单区域部署尤其脆弱。若唯一运行区域突然不可用，流水线会停止，直到区域恢复。具有自动故障转移能力的多地部署流水线，可能只需将处理或服务流量从受影响区域排空，等待故障结束。区域不可用时，数据可能滞留或延迟，使流水线输出错误，并破坏依赖作业或服务的输出正确性。

案例研究：Spotify

由伊戈尔·马拉维奇(IgorMaravić)撰写

Spotify 是全球领先的音乐流媒体公司。每天有数千万用户通过 Spotify 收听喜爱的歌曲、与朋友分享音乐并发现新艺人。

本案例研究描述了我们的事件投递系统，该系统负责可靠地收集从Spotify应用生成的检测数据。该系统产生的数据有助于我们更好地了解最终用户，并在适当的时间为他们提供适当的音乐。

说明

在此案例研究中，"客户"是指Spotify中使用事件投递系统中的数据的开发团队。"最终用户"是指使用Spotify服务收听音乐的个人。

事件投递

我们把最终用户的交互称为“事件”。每当用户收听歌曲、点击广告或关注播放列表，系统都会记录一个事件。Spotify 每天捕获并向服务器发布数千亿个不同类型的事件。这些事件用于 A/B 测试分析、展示播放次数和支持个性化发现播放列表等场景。最重要的是，我们依据已投递事件向艺人支付版税，因此必须具备可靠的事件存储和投递机制。6

在我们处理事件数据之前，需要收集该数据并将其投递到持久性存储中。我们使用事件投递系统来可靠地收集和保留所有已发布事件。事件投递系统是我们数据基础结构的核心支柱之一，因为我们几乎所有的数据处理(直接或间接)都依赖于它投递的数据。

所有投递的事件均按类型和发布时间进行划分。如图13-5所示，在任何给定小时内发布的事件都被分组在一起并存储在指定的目录中，该目录称为"已投递事件的小时桶"。然后将这些存储桶分为事件类型目录。这种分区方案简化了Spotify的数据访问控制，所有权，保留和使用。

小时桶是我们的数据作业与事件投递系统唯一的接口。因此，我们会根据每个事件类型的小时桶投递情况来衡量性能并为事件投递系统定义SLO。

事件投递系统的设计与架构

我们的小时桶位于Google Cloud Storage（GCS）上。在设计过程的早期，我们决定将数据收集与系统内的数据投递分离。为此，我们使用了一个全局分布的持久队列Google Cloud Pub/Sub 作为中间层。分离后，数据收集和投递将充当独立的故障域，从而限制了任何生产问题的影响，并导致了更具弹性的系统。图13-6描述了我们的事件投递系统的体系结构。

数据收集

生成的事件按事件类型分组。每种类型描述 Spotify 应用中的一种用户操作，例如订阅播放列表或开始播放歌曲。系统对事件类型实行完全隔离，确保不同类型互不影响。各类事件分别发布到 Google Cloud Pub/Sub 中为其分配的主题；发布操作由运行在 Spotify 数据中心和 Google Compute Engine（GCE）上的微服务执行。每条已发布事件流都由一个专用 ETL 进程实例处理并完成投递。7

提取、转换、加载

ETL流程负责将已发布的事件投递到GCS上正确的每小时桶。ETL过程包含三个步骤/组成部分：

  1. 专用微服务从事件流中消费事件。

  2. 另一个微服务将事件分配给它们的每小时分区。

  3. 在Dataproc上运行的批处理数据作业会从其每小时的分区中对事件去重，并将其写入 GCS 的最终位置。

每个ETL组件都有单一职责，这使这些组件更易于开发，测试和操作。

数据投递

事件类型的投递可由客户（即 Spotify 的其他工程团队）直接动态启用或停用。客户通过简单配置指定需要投递的事件类型。每当某类事件的投递状态改变，微服务就会动态申请或释放运行 ETL 所需的 Google Compute Engine（GCE）资源。下面是客户可启用或停用的事件类型配置示例：

events:
    -CollectionUpdate
    -AddedToCollection
    -RemovedFromCollection

当客户启用新事件类型的投递时，我们事先并不知道需要多少资源来保证投递。因此，手动确定必要的资源非常昂贵。为了实现投递不同事件类型的最佳资源利用率，我们使用了GCE Autoscaler 。

事件投递系统运维

为我们的事件投递系统定义和传达SLO可以通过三种方式提供帮助：

设计和开发

在开发我们的系统时，拥有明确的SLO可为我们朝着实现的目标迈进。这些目标可帮助我们做出务实的设计选择并优化系统以简化操作。

确定性能问题

一旦将系统部署到生产环境中，SLO将帮助我们确定系统的哪些部分运行不佳以及需要集中精力进行哪些工作。

设定客户期望

SLO使我们能够管理客户的期望并避免不必要的支持请求。当客户清楚我们系统的局限性时，他们有权决定如何设计，构建和操作依赖于我们数据的他们自己的系统。

我们为客户提供三类事件投递系统 SLO：及时性、完整性和偏斜度。它们以 GCS 中的小时桶为基础。为了尽可能客观，也避免给事件投递系统塞入无关功能，我们使用独立的外部系统衡量所有 SLO，例如下一节介绍的数据可视化工具 Datamon。

及时性

及时性 SLO 定义为投递一个小时桶所允许的最大延迟。投递延迟等于桶实际完成投递的时间，减去该桶理论上最早可以关闭的时间。图 13-7 展示了一个例子：图中有第 12、13、14 小时的桶；如果第 13 小时的桶在 14:53 关闭，则完成延迟为 53 分钟。

数据投递及时性是衡量数据流水线性能的指标。我们使用围绕小时桶构建的内部数据监控工具 Datamon 来衡量并可视化及时性。图 13-8 中，每个绿色矩形（灰度图中的绝大多数矩形）表示按时投递的小时桶；右侧聚集的灰色矩形表示尚未投递的桶；最上方一行的 3 个深色矩形原为红色，表示未在 SLO 期限内投递的桶。若一天的所有小时桶均成功投递，则显示为一个绿色矩形。

下游数据作业必须等所依赖的小时桶投递完成后才能开始处理。每个作业会在处理前定期检查依赖项的投递状态，因此任何投递延迟都会影响下游作业的及时性。客户非常重视数据按时到达。为便于故障期间安排事件投递优先级，我们把及时性 SLO 分为高、普通、低三个等级，由客户为各自的事件类型选择合适等级。

偏斜度

偏斜度 SLO 定义为每天最多允许有多大比例的数据被放入错误的桶。偏斜度和完整性是事件投递系统特有的概念，其他数据流水线并不使用。由于系统还处理涉及财务的事件，在设计之初就必须为这两个概念定义 SLO。其他事件采用尽力而为的投递，不提供相应 SLO。事件是否涉及财务由客户配置决定。

事件投递系统使用启发式方法判断小时桶应在何时投递，而启发式方法不可能始终完全正确。因此，本应属于此前已投递桶但尚未送达的事件，可能被投递到错误的后续小时桶；这种放错位置的事件称为“偏斜”。偏斜会让作业在某些时间段先低报、后高报数值，从而造成负面影响。图 13-9 展示了偏斜数据的投递。

完整性

分布式系统可能以多种方式丢失事件，例如新版本含有缺陷、云服务中断，或开发人员误删了已持久化的事件。为了及时发现数据丢失，我们衡量完整性；完整性定义为事件成功发布到系统后，最终得到投递的事件比例。

我们每天都会报告偏斜度和完整性。为了测量这些值，我们使用了内部审核系统，该系统比较所有已发布和已投递事件的计数。任何不匹配都会被报告，我们将采取适当的措施。

为了对及时性、偏斜度和完整性提供 SLO 保证，我们按服务器收到事件的时间把事件分配到小时桶，而不是采用客户端生成事件的时间。用户处于离线模式时，生成的事件可能先在客户端缓冲多达 30 天再发布；用户也可能修改设备系统时间，造成事件时间戳不准。因此，我们使用 Spotify 服务器的时间戳。

事件投递系统不对所投递事件的数据质量或准确性提供 SLO。我们发现，质量通常取决于事件内容，而内容由客户的业务逻辑填充。为了让系统随客户数量增长而扩展，我们始终让它专注于数据投递。可以把事件投递类比为邮政服务：邮件应按时、完好且未经拆封地送达。数据质量 SLO 则由拥有业务逻辑、理解数据内容的内部团队负责。

客户集成与支持

许多Spotify团队每天都与事件投递系统进行交互。为了鼓励推广使用并降低学习门槛，我们采取了以下步骤来简化用户与事件投递系统的交互：

事件投递作为完全托管的服务

我们希望避免向客户暴露系统的复杂性，让他们专注于他们要解决的特定问题。我们努力将任何系统复杂性隐藏在定义明确且易于理解的API 背后。

有限的功能

为了使我们的API简单，我们仅支持有限的功能集。事件只能以特定的内部格式发布，并且只能以单一序列化格式投递到小时桶。这些简单的API涵盖了我们的大多数用例。

每个事件的投递都需要明确启用

当客户启用事件的投递时，他们定义事件是否具有财务相关及其相关的及时性要求。此外，事件所有权需要明确地定义为启用过程的一部分。我们坚信，让我们的内部团队对他们产生的事件负责，可以提高数据质量。事件的明确所有权也使我们在事件发生时有清晰的沟通渠道。

无论与系统的交互多么简单，都需要良好的文档来提供良好的客户体验。在诸如Spotify之类的快节奏公司中，质量低下且陈旧的文档编制是一个常见问题。为了解决此问题，我们将文档与其他任何软件产品一样对待：收到我们团队的所有支持请求都将被视为文档问题或实际产品中的问题。大多数支持请求都与系统的公共API有关。我们在编写文档时尝试回答的一些问题示例包括：

  • 如何启用事件类型的投递？

  • 数据投递到哪里？

  • 数据如何分区？

  • 我们的SLO是什么？

  • 事件期间我们的客户应该期望什么样的支持？

我们的目标是随着客户群的增长而减少收到的支持请求量。

系统监控

监控我们的SLO可提供对系统总体运行状况的高级洞察。我们可靠的全面监控解决方案可确保在出现问题时始终向我们发出警报。使用SLO违规作为监控标准的主要问题是，我们在我们的客户受到影响 之后 会收到警报。为避免这种情况，我们需要对系统进行足够的操作监控，以在SLO损坏之前解决或缓解问题。

我们从基本的系统指标开始，然后发展到更复杂的指标，分别监控系统的各个组成部分。例如，我们监控CPU使用情况作为实例运行状况的信号。CPU使用率并非始终是最关键的资源，但它可以作为基本信号正常运行。

当我们试图了解和解决生产问题时，有时系统监控还不够。为了补充我们的监控数据，我们还维护应用日志。这些日志包含与它们描述的组件的运行和运行状况相关的重要信息。我们非常注意确保仅收集正确数量的日志数据，因为无关的日志很容易淹没有用的日志。例如，错误的日志记录实现可能会记录处理传入请求的高容量组件的所有传入请求。假设大多数请求是相似的，则记录每个请求不会增加太多价值。此外，如果记录了太多请求，将很难找到其他日志条目，磁盘填充速度更快，并且我们的服务的整体性能开始下降。更好的方法是对记录的请求数量进行速率限制，或者仅记录感兴趣的请求（例如导致未处理异常的请求)。

通过阅读应用日志来调试生产中的组件具有挑战性，应该是最后的手段。

容量规划

事件投递系统要全天候可靠运行，必须分配适量资源。所有组件部署在同一个 GCP 项目中并共享配额池，这一点尤其重要。我们通过容量规划确定每个系统组件需要多少资源。

大多数系统组件的容量规划以 CPU 使用率为依据。我们按高峰时段 CPU 使用率 50% 为各组件配置容量，以此留出安全余量应对突发流量。Spotify 自建数据中心时期采用静态资源配置，既在非高峰时段浪费资源，又无法应对大规模流量突增。为提高资源利用率，我们对部分无状态组件使用 GCE Autoscaler。

Autoscaler 上线初期并不顺利，在某些条件下甚至会引发故障。我们以 CPU 使用率作为自动扩缩容指标，这要求 CPU 使用率与每个组件实例完成的工作量高度相关。如果新增耗费大量 CPU 的守护进程，或实例空耗 CPU 却不做有效工作，二者关系就会被破坏，Autoscaler 便会启动过多实例。

如果 CPU 使用率持续上升却与实际工作量无关，Autoscaler 会不断扩容，直到耗尽所有可用资源。为防止它用尽配额，我们采取了以下措施：

  • 我们限制了Autoscaler可以使用的最大实例数。

  • 我们严格限制了实例上运行的所有守护程序的CPU使用率。

  • 一旦我们发现没有任何有用的工作在做，我们就会积极地限制组件的CPU使用率。

即使使用Autoscaler，我们也需要进行容量规划。我们需要确保有足够的配额，并且将Autoscaler可以使用的最大实例数设置得足够高，以在高峰期间为流量提供服务，但又要足够低，以限制"失控"自动扩缩容的影响。

开发流程

为了快速交付新功能和改进，我们按照持续集成与持续交付（CI/CD）流程开发图 13-10 所示的事件投递系统。经过验证或评审的有效系统变更会尽快部署。要让每项变更成功上线而不损害 SLO，充分的测试覆盖是必要前提。

我们遵循“测试金字塔”理念：每个组件都有大量关注内部实现的单元测试，以及少量关注公共 API 的集成测试。金字塔顶层是系统级端到端测试；其中所有组件均视为黑盒，使测试环境尽可能接近生产环境。

初步开发后，每项更改都要经过同行评审。作为检查过程的一部分，所有测试都在共享的CI/CD服务器上执行，并将结果呈现给开发人员。只有在审阅者批准更改并成功通过所有测试之后，才能合并更改。合并更改后，将立即触发部署过程。

事件投递系统是 Spotify 基础设施的关键组件；一旦停止投递，Spotify 的所有数据处理都会停滞。因此，我们对部署采取更保守的方式，分阶段发布每项变更，并要求人工批准后才能进入下一阶段。

在第一个部署阶段，将更改部署到预发布环境。这种低风险的预发布系统无法处理生产流量。出于测试目的，生产流量的代表部分被镜像到预发布系统中，该系统是生产中运行的系统的副本。在第二个部署阶段，将更改部署到生产实例或金丝雀的一小部分。只有在确保一切都顺利进行之后，我们才执行完整的生产部署，无论是演练还是金丝雀(请参阅第16章)。

事件处置

处理故障事件时，首要任务是减轻损害，让系统恢复到先前的稳定状态。为避免情况恶化，故障期间不对组件部署重大变更。唯一的例外是确认故障由最近部署的新代码引起，此时应立即回滚到此前可正常工作的版本。

今天，我们遇到的最常见的操作故障是由系统故障（例如，我们引入软件错误或性能下降)或我们所依赖的外部服务故障（例如，对服务API的更新不能向后兼容或服务打破了其SLO)。我们使用了许多经过考验的Google Cloud和内部Spotify服务，例如Cloud Pub/Sub和 Helios ，以加快我们系统的开发速度并减轻我们的运维负担。如果因外部服务而导致故障，我们将有一个专职的值班团队 提供支持。使用外部服务的缺点之一是我们无法自己缓解问题。此外，在发生事件期间，将问题传达给第三方需要花费宝贵的时间。不过，我们认为，把偶尔无力的感觉委派给第三方是值得的。8

重负载下意外的系统行为是操作失败的另一个常见原因。在精确的生产条件下测试服务是不可能的，因此很难预测所有可能发生的情况。模仿我们的组件在生产中面临的负载也可能很困难。高负载加上无法预料的边缘情况可能会导致有趣的故障情况，例如前面在前文的"容量规划"中描述的Autoscaler示例。

系统运行故障可能导致 SLO 违约。若只是数据新鲜度 SLO 违约，客户无需采取行动，只要等待数据到达；但若偏斜度或完整性 SLO 违约，数据质量已经受损，可能需要客户参与。当检测到完整性或偏斜问题时，必须正确重处理受影响的事件：

  • 为了处理不完整性，需要从已知良好的最后一个检查点重新发送事件。

  • 为了解决过度偏斜的问题，已投递的事件将重新安排并分配给其正确的小时桶。

重新投递和重新安排事件都是手动完成的。修改已投递事件后，我们强烈建议客户对其进行重新处理以产生足够质量的数据。

总结

多年来，Spotify 的事件投递系统不断演进。早期版本远不够可靠，工程师几乎每隔几晚就会被呼叫，大多数开发迭代都耗在事件补救和事后总结上。设计当前版本时，我们专注于构建模块化系统，把一项核心任务做好：投递事件。我们还希望把事件投递作为产品提供给 Spotify 其他团队，因此必须定义并满足 SLO，为客户设定明确预期。

我们采用多种策略维持服务运行，从文档完备的值班流程，到使用经过充分验证的外部服务（如 Google Cloud Pub/Sub）。此外，由同一个团队负责系统全生命周期的开发与运行，使团队能够把维护系统积累的经验持续用于改进系统。

由于这些努力，我们现在有了一个可靠的系统，使我们可以将时间集中在满足更雄心勃勃的完整性，偏斜度和及时性的SLO上。这导致更好的可用性和更好的整体客户体验。

结语

把 SRE 最佳实践用于流水线，有助于做出明智的设计选择并开发自动化工具，使流水线更易运维、更高效地扩展，也更加可靠。Spotify 的事件投递系统就是一个遵循核心 SRE 原则建设和运行的流水线示例，它综合采用内部、Google Cloud 和第三方技术，满足客户对数据处理及时性的要求。若忽视运维最佳实践，流水线更容易失败，并在增长、迁移、功能发布或故障清理期间产生大量人工工作。与任何复杂系统设计一样，必须理解需求、选择要维持的 SLO、评估可用技术，并记录设计与常见任务的操作方法。
